### 核心技术决策（9 项差异 D1–D9）
- **D1（重大）**：Prophet 不作主基线。理由：Prophet 建模的是"时间的函数"而非"降雨的函数"，无法回答"未来下 30mm 会涨多少"；每次预测需重新 fit Stan（秒级~十秒级），无法满足 5 分钟滚动预测；cmdstanpy 在 Windows 安装失败率高。改为 **LightGBM 预测水位增量 Δlevel**（树模型不能外推绝对值，但增量可叠加外推，且消除站点基准面差异、可多站共享模型）。Prophet 降为冷启动兜底（对差分序列建模）。升级位：PyTorch **TCN** 优先于 LSTM。
- **D2**：本期不用时序数据库。10 站点×5min×1年 ≈ 105 万行，SQLite 足够。生产阶段 TimescaleDB（首选）/ IoTDB（信创）。
- **D4（不补则校准模块无法实现）**：Forecast 表只存 peak_level，需新增 `forecast_point` 逐点明细表（含 `actual_level` 事后回填），用于逐点 RMSE 与指标计算。
- **D5**：指标体系增加**峰值误差、峰值时间误差、POD/FAR/CSI**，不只 RMSE/MAE。峰值时间误差是内涝预警最关键指标。
- **D6**：模拟数据必须用**简化概念性水文模型**生成（降雨事件→产流→单位线汇流→指数退水→水位映射），保证降雨与水位因果一致，且生成器内部真值可直接作 ground truth。
- D3/D7/D8/D9：单连接 WS、TCN 优先、部署先脚本后 Docker、Pinia 本期可不引入。

## V1.1 修订（同日）：定位澄清 —— 改为「脚手架 + 可运行原型」

**用户澄清**：老师说 demo 只是把项目骨架搭起来，不严格要求实际模型，先把脚手架、前端原型、后端留白接口做好，数据模拟即可。

**据此重排取舍重心**（文档已重写为 V1.1）：

- **三层交付边界**（核心框架）：
  - 骨架层（必须做实）：目录结构、模块边界、接口契约、数据模型、配置外置、异常处理、日志
  - 原型层（形态到位、逻辑可简）：四前端页面、全部 REST 接口、预测→预警演示链路
  - 占位层（留白）：真实数据源、真实算法、推送、权限、自动校准
- **第一原则：占位 ≠ 缺失** —— 留白必须有接口定义 + 占位实现 + 扩展点标注。统一标记 `# EXT-POINT(类型): 说明`，类型限 DATASOURCE / MODEL / ALGORITHM / INTEGRATION，`grep EXT-POINT` 可列出全部待填位点。
- **D1 口径变更（关键）**：从"Prophet 必须换 LightGBM"改为"**本期不装任何有安装风险的模型**"。Prophet 的问题不是算法，是 `cmdstanpy` 在 Windows 安装失败率高 → 违反 NFR-1。占位模型改为零依赖的 **NaiveModel + LinearResponseModel**（纯 numpy）。Prophet/LightGBM/TCN 仅留实现位。
  - LinearResponseModel: `Δlevel(t+h) = Σ wᵢ·rain(t−i) − k·(level − base)`，体现降雨驱动+滞后+退水，二十行代码，演示曲线形态可信。
- **模拟数据降级**：不再要求完整水文机理，只要求形态合理；且**生成器与 LinearResponseModel 共用同一套参数**，成本几乎为零，附带可注入极端降雨事件做预警演示。
- **FR-6 校准整体降为占位**，但 `forecast_point` 明细表仍是 M（属数据模型正确性，不属功能优先级）。
- **新增**：场景 S7「模型可插拔演示」；NFR-1 可安装（最高优先级）；ADR-5 前端 mock 双通道（`VITE_USE_MOCK`）；ADR-6 依赖清单白/黑名单；§2.4 留白接口清单（12 个接口逐条标注真实现/留白）。
- **里程碑重排**：M1 骨架 → M2 数据链路 → M3 前端原型（mock，可与 M2 并行）→ M4 预测预警链路 → M5 可选增补。重心在 M1 与 M4。
- **明确不引入**：prophet、torch、celery/redis、时序数据库集群、地图（涉合规审图号 + 政务内网无公网瓦片）。Python 锁 3.11。
