## V1.2 架构升级 + 前后端规划书 V2.0（同日第二轮）

**用户新要求**：① 架构要好一点、先进一点、可支持扩充；② 后续要做成 **Agent 项目**，不只是基本技术考虑。

（技术选型主文档顶部已加 V1.2 指针；V1.1 三层边界与硬约束**全部保留**，V1.2 是增强不是推翻）

### 核心决策
- **架构范式**：模块化单体 + 端口适配器（六边形）。物理单进程、逻辑按领域切分，将来可拆。**不拆微服务**。
- **四个核心抽象**（V1.1 的两个 → 四个）：`DataSource` / `ForecastModel` / **`Tool`（本期做实）** / **`Agent`（占位）**。铁律：应用层与领域层不得 import 具体 Adapter。
- **Tool 是四个里唯一本期做实的**：它就是现有 Service 的声明式包装，成本近零；本期即可用 EchoAgent 演示"提问→选工具→执行→回答"完整链路。
- **本期不引入 Agent 框架**（LangChain/LangGraph/AutoGen）：框架迭代快、依赖重；**Agent 成败在数据和工具不在框架**，先把资产沉淀好。
- **Agent 能力分级 L0–L3**：L0 只读 / L1 生成 / L2 建议变更（**必须人工确认**）/ **L3 自动执行永久不做**（防汛高后果场景，责任归属必须由人承担）。
- **SSE 优先于 WebSocket**：Agent token 流 + 事件推送用 SSE（单向、HTTP、浏览器原生重连、穿透网关好）。WebSocket 只在高频双向时才考虑。

### 技术栈升级
- 后端：Alembic 迁移、**DuckDB**（分析查询，直接读 Parquet，零服务零迁移，~30MB 纯 wheel，不违反 NFR-1）、structlog 结构化日志（trace_id 贯穿）、FastAPI Depends 依赖注入、任务表
- 前端：**TypeScript**、**Pinia（V1.1 曾决定不引入，V1.2 反转）**、**openapi-typescript 自动生成类型与 client**、VueUse、SSE composable、Agent 控制台占位页
- Pinia 反转理由：Agent 会话是跨页面共享有状态数据 + SSE 需在组件外累积状态；属新需求导致的前置条件变化，已在文档记录

### 新增数据模型
- `flood_event`（内涝事件库，供 Agent 历史类比检索 + 极端样本来源 + 演示回放）
- `agent_session` / `agent_message` / `agent_tool_call`（trace；tool_call 兼作系统操作审计日志）
- 关键字段：`alert.lead_minutes_advantage`（预警提前量）、`forecast_point.actual_level`（已有）
- 新增错误码 1601 TOOL_NOT_FOUND / 1602 TOOL_CONFIRM_REQUIRED

### 最重要的判断
**Agent 项目的真正瓶颈是数据不是框架**。本系统恰好在生产结构化资产（预测-实况对齐、事件库、阈值口径），应先把资产沉淀好，Agent 是水到渠成的最后一层。很多 Agent 项目失败在先搭框架再找数据。

### 里程碑调整
M3 从"前端原型"扩为"前端原型 + 工具层（ToolRegistry + EchoAgent）"；M5 增补 DuckDB/SSE/MCP/指标计算。

## V1.3 需求覆盖核对与三缺口补齐（同日第三轮）

**用户提供了一份需求书 → 规划映射核对表**，指出 3 个 ❓ + 1 个 🔶：① "智能体" 语义可能错位（需求书里"智能体"跟预测模型并列，指自适应/自融合，不是对话式 Agent）；② 多源协同修正只有"滚动预测"无显式校正机制；③ 6h/12h 对需求书是缩水；附：模型校准只有占位、在线学习未提及。

**用户明确要求：把不够完善的地方做充分，不要留下待补充事项。**

**产出**：`docs/需求覆盖核对与缺口补齐_V1.3.md`，并同步修改 4 份文档（后端规划书→V2.1、架构文档、验收标准、技术选型主文档加 V1.3 指针）

### 三个缺口的补齐方案（关键，后续别再重新讨论）
- **① 智能体 → 双层 Agent 架构，不做二选一**
  - **Agent-A 预测编排智能体 `ForecastOrchestrator`**：对应"时序预测模型+智能体"。五项决策：D1 模型自适应选择 / D2 多源融合权重 / D3 修正策略 / D4 置信区间自适应 / D5 降级决策。**本期 `RuleBasedOrchestrator` 纯规则零依赖做实，不需要 LLM 不联网**。决策写 `forecast_decision` 表（含 reason 人话解释）。
  - **Agent-B 交互智能体**：V1.2 已有，占位。
  - 打通方式：Agent-B 新增 `explain_forecast` 工具，读 `forecast_decision` 把 Agent-A 决策翻译成人话。
- **② 多源协同修正 → `ForecastRevisionService`**
  - 三类触发：T1 新实测 / T2 新预报 / T3 事件状态变化（正好对应需求书"实时监测、最新预报、已发生事件"）
  - 算法：**多源加权新息 + 时间衰减** `corrected(t) = predicted(t) + α·e·ρ^Δt`，α≈0.6，ρ≈0.85/步，只对 Δt>0 生效；e 由各源新息按 Agent-A 的 D2 权重加权合成（这就是"多源协同"的字面实现）
  - 存储：`forecast_point` 加 `pred_level_raw` + `revision`，`pred_level` 改为修正后值。**顺带解决了 FR-3.7「原始与平滑后同时保存」，不用加表**
  - **在线学习的落点在此**：预测级在线适应 ✅ 做实；模型级增量训练 ❌ 明确不做（小样本强非平稳易发散，一旦发散演示就崩；预测级修正可随时关闭）
- **③ 6h/12h → 模拟源产出降雨预报序列，本期跑通**
  - `rain_observed(t)` + `rain_forecast(t_issue, h)`，误差建模 `ε(h)` 随 h 单调增大，可加对峰值的系统性低估（真实 NWP 典型缺陷）
  - 效果：可见"预见期越长置信区间越宽"，这本身就是好演示点
  - 研判配套：6h/12h 预警标 `alert.is_reference=1`（参考级，浅色、不计入统计、不推送），防误报风暴
  - 撤回成本：config 里 lead_hours 改成 [1,3] 即可，代码不动
- **附：校准拆三项** —— 重训 🔶 占位；**参数校准 ✅ 做实**（numpy 网格/随机搜索标定 wᵢ 与 k，秒级）；在线学习 → 即预测级修正 ✅

### 结果
需求书逐条核对从 3❓+1🔶 → **全部 ✅**。三个补齐**零新增依赖**（规则驱动 / 几十行 numpy / 生成器多一路输出）。
