## 1. 先纠正一个前提：定位其实已经清楚了

你之前已经澄清过老师的口径：**"demo 只是把项目骨架搭起来，不严格要求实际模型，先把脚手架、前端原型、后端留白接口做好，数据模拟即可。"**

这句话信息量其实很大，它已经排除了大部分歧义：

| 已明确 | 推论 |
|---|---|
| 不严格要求实际模型 | 不用在算法选型、调参、精度上耗时间 |
| 脚手架要搭起来 | **工程结构本身是交付物**，不是手段 |
| 前端原型要出来 | 五个页面要能看、能点、能演示 |
| 后端留白接口 | **"留白"也是交付物**，且必须留得规范 |
| 数据模拟即可 | 不需要真实数据源 |

**所以真正缺失的不是"方向"，而是"完成的定义"（Definition of Done）**——做到哪一步可以停手、可以拿去给老师看。这才是要补的东西。

---

## 2. 为什么不该等老师给标准

三条现实理由：

1. **老师多半给不出来**。他说"做个 demo"时脑子里通常只有模糊预期，要他把验收标准写出来，他自己也得想半天，大概率拖到答辩。
2. **等的过程是纯亏损**。这段时间什么都不做，最后可能还要返工。
3. **但老师的评判权还在**。所以正确做法不是"替他决定"，而是**你提草案、让他做增删改**。

> **给选项，不要提开放问题。**
> 问"老师您想要什么标准" → 他不知道怎么答 → 拖。
> 发一份勾选清单过去 → 他划掉两条、加一条 → 十分钟搞定。

第 7 节有一段可以直接复制发送的话术。

## 3. 验收标准草案（按三层边界组织）

沿用 V1.1 §0.1 的三层划分。三层的验收标准**性质完全不同**——这是这套验收设计的核心：

| 层 | 老师在什么时候评判 | 评判依据 |
|---|---|---|
| 骨架层 | 翻代码时 | 结构是否合理、扩展点是否清楚 |
| 原型层 | 看演示时 | 界面是否完整、链路是否跑通 |
| 占位层 | 翻代码 + 听你讲 | **是不是"看得见形状的空位"** |

### 3.1 骨架层验收（老师翻代码时看这些）

- [ ] 前后端目录结构清晰，模块职责单一，新人能看懂往哪填代码
- [ ] `DataSource` 抽象接口完整，`SimulatedSource` 真实现、`RealSourceAdapter` 有完整签名与 TODO
- [ ] `ForecastModel` 抽象接口完整，至少 2 个占位实现可切换
- [ ] 数据模型 DDL 完整，且**包含 `forecast_point` 逐点明细表**
- [ ] 统一响应结构 `{code, message, data}` 与错误码表，所有接口一致
- [ ] 配置外置：数据源类型、模型类型、点位、阈值、预见期全在配置文件里，改配置不改代码
- [ ] `/api/v1/health` 返回数据源 / 模型 / 数据库三态
- [ ] 异常处理框架到位：数据源断流、模型失败、数据库失败均有捕获与降级
- [ ] 日志输出规范，能看出一次预测的完整生命周期
- [ ] **预测编排决策可追溯**：`forecast_decision` 表记录模型选择、融合权重、修正强度与理由（V1.3）
- [ ] 数据源质量变化时融合权重随之变化（可注入数据缺失演示）（V1.3）
- [ ] `forecast_point` 同时保存 `pred_level_raw` / `revision` / `pred_level`（V1.3）
- [ ] 模型级在线学习明确标注"不做 + 理由"，而非留白不明（V1.3）

### 3.2 原型层验收（老师看演示时看这些）

- [ ] 一条命令启动，2 分钟内可通过浏览器访问
- [ ] 内置 5–8 个监测点，具备不同响应特征（低洼易涝 / 一般道路 / 河道断面）
- [ ] 总览页：监测点卡片（当前水位 + 预警色标）、今日预警统计、数据源与模型状态
- [ ] 详情页：历史水位曲线（实线）+ 预测曲线（虚线）+ 四级阈值线（蓝/黄/橙/红）
- [ ] 支持 1h / 3h / 6h / 12h 预见期切换，且**预见期越长置信区间越宽**（V1.3）
- [ ] 详情页可同屏显示**原始预测曲线与修正后预测曲线**（体现多源协同修正）（V1.3）
- [ ] 6h / 12h 预警标记"参考级"，界面浅色区分、不计入有效预警统计（V1.3）
- [ ] 点"发起预测" → 出曲线 → 超阈值 → 出预警 → 预警中心可见（**这条链路必须现场跑通**）
- [ ] 预警中心展示预警记录、等级、触发原因、时间、状态
- [ ] 设置页可改阈值，改完下一次预测按新阈值研判（证明配置真实生效）
- [ ] 可切换占位模型，预测曲线随之变化（**场景 S7，本期最有说服力的演示点**）
- [ ] 断开数据源 → 显示断流提示且不崩溃；恢复 → 自动重连
- [ ] 后端不启动时，前端靠 mock 仍能完整演示五个页面

### 3.3 占位层验收（最容易被忽略，也最能体现工程素养）

- [ ] 每一处留白都有：完整接口签名 + 符合契约的返回 + 扩展点标注
- [ ] 统一标记 `# EXT-POINT(类型): 说明`，类型限 `DATASOURCE / MODEL / ALGORITHM / INTEGRATION / AGENT`
- [ ] `grep EXT-POINT` 能一次性列出全部待填位点（**建议现场演示这条命令**）
- [ ] `/api/v1/calibrations` 返回 `status: pending` 而非 404 或报错
- [ ] 占位模型的返回结构与将来真模型**完全一致**（points / peak_level / confidence_interval 一个不少）
- [ ] Agent-B（对话式）接口与 Tool 注册表就位，`explain_forecast` 可解释 Agent-A 的决策（V1.3）

> **这一层是整个交付的隐藏加分项。** 大多数同学做到"能跑"就停了，留白处要么空着要么随便写死。你把这些空位留得规范，老师一眼就能看出这是"有计划的未完成"，而不是"做不下去了"。

### 3.4 文档验收

- [ ] 需求分析文档（V1.1 已有）
- [ ] 技术选型文档（V1.1 已有）
- [ ] 数据库设计说明（含 DDL）
- [ ] 接口文档（FastAPI 自带 OpenAPI，需补字段说明）
- [ ] 部署与运行说明（一条命令怎么跑）
- [ ] **演示脚本**（第 4 节）
- [ ] README：让人照着就能上手填代码

## 4. 三分钟演示剧本

老师看 demo 通常不超过 5 分钟。**必须有剧本，不能现场即兴点。**

| 时间 | 动作 | 要说的话 |
|---|---|---|
| 0:00–0:20 | 打开总览页 | "这个系统解决的是'等看到涨水已经来不及处置'的问题——把监测变成预测。" |
| 0:20–0:50 | 展示监测点卡片 | "这是 6 个监测点，低洼点涨得最快，已经黄色预警。" |
| 0:50–1:30 | 下钻详情页，切 1h/3h/6h/12h | "实线是历史，虚线是预测，四条横线是四级阈值。预见期越长，置信区间越宽——长预见期的不确定性更大。" |
| 1:30–2:00 | 展示协同修正 | "细虚线是模型原始输出，粗虚线是经过多源修正后的预测——新实测到了，系统会用它修正还没发生的预测，修正效果直接可见。" |
| 2:00–2:30 | 点"发起预测"，触发预警 | "点预测 → 出曲线 → 峰值超橙线 → 预警中心马上生成记录。6h/12h 的预警标为参考级，浅色显示，不干扰有效预警。" |
| 2:30–3:00 | 展示 Agent-A 决策 + 占位层 | "这个面板显示系统为什么选这个模型、融合权重是多少——不需要 LLM，规则驱动的编排智能体。`grep EXT-POINT` 能列出所有待填位点。" |

> 收尾落在"占位规范 + 智能体特性"上，比落在"预测多准"上更稳——因为模型本来就不是本期交付重点，硬吹精度反而容易被追问。

## 5. 演示时几乎必被问的四个问题（提前准备答案）

| 问题 | 标准答案 | 现场怎么证明 |
|---|---|---|
| **"数据是假的吧？怎么证明有用？"** | 数据源是抽象接口，`SimulatedSource` 与 `RealSourceAdapter` 实现同一套方法；生成器与占位模型共用同一组参数，保证形态一致。接真实数据只需新增实现类 + 改一行配置。 | 打开 `datasource/` 目录，指两个类的同名方法 |
| **"预测模型是什么？为什么用它？"** | 本期骨架重点是接口与链路，模型是**占位实现**（Naive / LinearResponse）。LinearResponse 体现降雨驱动 + 滞后 + 退水，形态上可信；真模型的实现类位置已留好。 | 打开 `algorithms/model/`，指 `EXT-POINT(MODEL)` 标注 |
| **"跟直接设个阈值报警有什么区别？"** | **预警提前量**。阈值报警要等水位实测涨到 2.50 m 才响；系统在 1.82 m 时依据降雨预测 40 分钟后将达 2.63 m，提前报警。 | 详情页显示"本次预警较阈值报警提前 XX 分钟" |
| **"做完到什么程度了？接下来怎么继续？"** | `grep EXT-POINT` 列出全部待填位点，每个都有接口签名、返回契约和填充说明。 | **现场跑这条命令** |

> 第 4 个问题的答案就是第 4 个问题的价值所在——**"有计划的未完成"本身就是可交付的成果**。

## 6. 时间不够时的砍减顺序

如果临近交付发现做不完，**按这个顺序砍，绝不能反向砍**：

| 顺序 | 砍什么 | 理由 |
|---|---|---|
| 1 | M5 全部：Docker Compose、单元测试、指标计算、README 精修 | 演示看不到，纯加分项 |
| 2 | 设置页复杂交互 → 退化为配置文件 + 简单表单 | 阈值可配置这个"点"保住即可 |
| 3 | 6h / 12h 预见期 → 只留 1h / 3h（`config.yaml` 改 `lead_hours: [1,3]`） | 6h/12h 已用模拟预报序列跑通，但时间紧时可先砍，损失"预见期越长区间越宽"与"参考级预警"两个演示点（V1.2 修正口径） |
| 4 | 预警中心筛选 → 只留列表 | 列表已能证明记录生成 |
| 5 | 监测点数量 8 → 5 | 卡片列表效果差别不大 |

**绝不砍（砍了骨架就不成立）**：
- `DataSource` 与 `ForecastModel` 两个抽象
- `forecast_point` 明细表（将来补做要重构存储层）
- 前端页面能跑
- predict → 协同修正 → alert 完整链路
- `EXT-POINT` 标注
- `forecast_decision` 决策表（Agent-A 可追溯，V1.3 新增）

## 9. 一条可选加分项：把"预警提前量"做成演示亮点

成本很低，但能显著提升说服力，建议加。

**定义**：`预警提前量 = 传统阈值报警触发时刻 − 本系统预警触发时刻`

**举例**：某点阈值 2.50 m。传统方式等实测涨到 2.50 m 才报警（T1）；本系统在水位 1.82 m 时依据降雨预测 40 分钟后达 2.63 m，提前报警（T0）。**预警提前量 = 40 分钟。**

**为什么值得加**：
1. 这是**业务语言**。老师听得懂"多争取 40 分钟处置时间"，听不懂 RMSE 0.08 m 意味着什么。
2. 它一句话回答了"你这东西到底有什么用"。
3. 占位模型就能算出来，不依赖真实精度。

**落地方式**：详情页显著位置展示"本次预警较阈值报警提前 XX 分钟"。
