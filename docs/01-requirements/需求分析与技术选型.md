## 0.1 定位澄清 —— 本期交付的是"脚手架 + 可运行原型"

**本期不考核模型的实际精度。目标是：把项目骨架、前端原型、后端留白接口搭起来，数据用模拟的。**

这条澄清改变了所有技术取舍的重心。新的交付物分三层，**三层的验收标准不同**——这一点必须在动手前统一认识，否则会出现"该潦草的地方过度投入、该做实的地方草草了事"：

| 层 | 内容 | 验收标准 | 典型例子 |
|---|---|---|---|
| **骨架层**（必须做实） | 目录结构、模块边界、接口契约、数据模型、配置外置、异常处理框架、日志 | 结构合理、职责单一、扩展点明确，新人能看懂往哪填 | `DataSource` 抽象接口 + `SimulatedSource` 实现；统一响应结构 `{code,message,data}` |
| **原型层**（形态到位，逻辑可简） | 四个前端页面、全部 REST 接口、"预测 → 预警"演示链路 | UI 元素完整、接口返回符合契约、演示跑得通 | 详情页历史曲线+预测曲线+四级阈值线全画出来，预测值由占位模型给出 |
| **占位层**（留白） | 真实数据源、真实预测算法、推送、权限、自动校准 | **有接口定义 + 有占位实现 + 有扩展点标注** | `RealSourceAdapter` 只有方法签名与 TODO；`/api/v1/calibrations` 返回 `pending` |

由此确立本期第一原则：

> **占位 ≠ 缺失。** 每一处留白都必须是"看得见形状的空位"：接口签名完整、能返回符合契约的假数据、并明确标注将来替换成什么。评审时要能一眼看出"这里将来填什么、怎么填"。

以及三条派生工程原则：

1. **依赖极简** —— 脚手架阶段只用"装得上、跑得动"的包。任何存在安装失败风险的依赖一律不进 `requirements.txt`。一条命令跑不起来，骨架就是失败的。
2. **前后端可独立启动** —— 前端靠 mock 能独立跑完四个页面，后端靠占位模型能独立返回全部接口，两边互不阻塞。
3. **配置驱动一切** —— 数据源类型、模型类型、点位、阈值全部外置。将来接真实数据、升级真实模型，是"改配置 + 填一个实现类"，不是"改结构"。

# 第一部分：需求分析

## 1.1 业务背景

城市内涝治理正从"事后处置"转向"事前预报预警"（调研报告 1.1/1.4）。本系统面向城市防汛场景，融合降雨实况、气象预报、雷达、水位监测等多源数据，预测未来 1h/3h/6h/12h 水位并输出分级预警。

**本期目标**：交付一套覆盖"数据接入 → 数据治理 → 水位预测 → 阈值研判 → 预警发布 → 模型校准"完整链路的**工程骨架与可运行原型**，为后续接入真实数据、升级真实模型提供可直接填充的结构。

## 1.2 目标用户与角色

| 角色 | 身份 | 使用频率 | 核心诉求 |
|---|---|---|---|
| **防汛值班员**（主用户） | 防汛办/城管值班人员 | 汛期高频 | 一眼看清"哪个点要淹、什么时候淹、淹到什么程度" |
| **防汛指挥/管理者** | 防汛办负责人 | 汛期中频 | 看全局态势与预警统计，做资源调度决策 |
| **系统管理员** | 实施/运维人员 | 低频 | 配点位、配阈值、配数据源，一键部署与排障 |
| **模型工程师**（后续接手者） | 算法开发 | 中频 | **换模型、看误差、重训、回滚**——骨架必须让他无缝接手 |
| **评审方**（老师/甲方） | 验收 | 一次性 | **结构完整、演示稳定、扩展点清晰**，技术路线说得通 |

> 本期需求重点向第 4、5 类角色倾斜：**骨架的可读性与可扩展性，优先于功能的深度。**

## 1.3 用户痛点

**防汛值班员**
- P1：只有实时水位监测，看到涨水时已来不及处置 → 需要预见期
- P2：多监测点来回切换容易漏看 → 需要一屏总览 + 等级色标
- P3：不知道预警怎么算出来的，不敢上报 → 需要触发原因可解释
- P4：预警频繁误报导致"狼来了"效应 → 需要等级与持续时长联合判定

**系统管理员**
- P5：阈值写死在代码里，换场景要改代码 → 需要配置外置
- P6：现场无外网、无专业运维 → 需要一条命令启动

**模型工程师（后续接手）**
- P7：预测结果无法与实况对齐评估 → 需要逐点保存预测明细
- P8：换模型就要动业务代码 → 需要统一模型接口 + 版本管理

## 1.4 核心使用场景

| 编号 | 场景 | 触发 | 用户动作 | 系统响应 | 成功结果 |
|---|---|---|---|---|---|
| S1 | 日常值守 | 汛期值班 | 打开总览页 | 展示全部点位当前水位 + 预警色标 + 系统状态 | 数秒内判断全局是否安全 |
| S2 | 点位下钻 | 某点预警或水位异常 | 点击查看详情 | 渲染历史曲线 + 预测曲线 + 四级阈值线 | 看出未来峰值与出现时间 |
| S3 | 主动预测 | 收到气象降雨预警 | 选择预见期并点击"发起预测" | 返回预测序列 + 置信区间 + 预警等级 | 得到可用于演示的完整结论 |
| S4 | 滚动预测 | 系统自动（每 5 min） | 无需操作 | 自动刷新全部启用点位预测与预警 | 演示期间无需手动操作 |
| S5 | 预警处置 | 预警生成 | 在预警中心查看并标记处置 | 展示预警列表、等级、原因、状态 | 预警闭环可追溯 |
| S6 | 阈值调整 | 场景变化/误报 | 在设置页改某点位阈值 | 配置生效，下次研判按新阈值执行 | 不改代码适配新场景 |
| S7 | 模型替换演示 | 演示模型可插拔 | 在设置页切换模型 | 同一接口返回不同模型的预测曲线 | 证明"模型接口可替换" |
| S8 | 故障恢复 | 数据源断流 | 无（系统自动） | 标记 ERROR、暂停预测、前端降级提示 | 不崩溃、不输出错误预测 |

> **S7 是本期新增的关键场景**。既然模型不是交付重点，那么**"模型可插拔"本身就是最有说服力的演示**——它直接证明骨架是对的。

## 1.5 成功度量（分层）

| 类别 | 指标 | 目标值 | 是否本期硬指标 |
|---|---|---|---|
| **骨架完整性** | 三层交付物齐全度 | 骨架层 100%、原型层 100%、占位层 100% 有标注 | ✅ 硬指标 |
| **可运行性** | `pip install -r requirements.txt` 一次性成功 | 100%（Windows + Linux） | ✅ 硬指标 |
| **可运行性** | 一条命令启动到页面可访问 | ≤ 3 步、≤ 2 分钟 | ✅ 硬指标 |
| **接口契约** | REST 接口返回结构与文档一致率 | 100% | ✅ 硬指标 |
| **演示稳定性** | 连续运行 2 小时无崩溃 | 100% | ✅ 硬指标 |
| **可扩展性** | 替换模型是否需要改业务代码 | 否（仅新增实现类 + 改配置） | ✅ 硬指标 |
| 预测精度 | 1h 预见期 RMSE | 待定 | ❌ 本期不考核 |
| 预测精度 | 峰值水位误差 / 峰值时间误差 | 待定 | ❌ 本期不考核（但计算口径须预留） |
| 预警质量 | POD / FAR / CSI | 待业务方给定 | ❌ 本期不考核 |

> **说明**：V1.0 曾把 RMSE 等指标列为核心目标，V1.1 依据定位澄清下调。但**指标计算口径必须在数据模型中预留**（即 FR-3.4 的逐点明细表），否则将来补做要重构存储层。

## 1.6 功能需求清单（EARS 格式，含优先级）

优先级 **M**=本期必须做实 / **S**=形态到位逻辑可简 / **P**=占位留白 / **W**=本期不做。

### FR-1 数据接入（骨架层）

| 编号 | 需求描述（EARS） | 优先级 |
|---|---|---|
| FR-1.1 | 系统应支持通过配置切换数据源类型（simulated / real），切换不改业务代码。 | M |
| FR-1.2 | 当数据源处于 STREAMING 状态时，系统应以配置采样间隔（默认 5 min）持续采集水位与降雨数据。 | M |
| FR-1.3 | 若数据源连续 3 个采样周期无数据或响应超时，则系统应将数据源状态置为 ERROR、暂停预测任务，并在前端显示断流提示。 | M |
| FR-1.4 | 若数据源由 ERROR 恢复可用，则系统应自动重连并恢复预测任务，无需人工干预。 | M |
| FR-1.5 | 数据源应实现统一适配接口（connect / disconnect / start_stream / stop_stream / get_status）；真实数据源通过新增 Adapter 接入，`RealSourceAdapter` 本期以占位形式提供。 | M（接口）/ P（真实实现） |

### FR-2 数据治理（骨架层 + 简化实现）

| 编号 | 需求描述（EARS） | 优先级 |
|---|---|---|
| FR-2.1 | 系统应将多源数据统一到固定时间粒度（默认 5 min）并对齐时间戳。 | M |
| FR-2.2 | 若水位采样值超出物理量程，或与前一采样点变化率超过配置阈值，则系统应将该点标记为异常并按缺失处理。 | M |
| FR-2.3 | 若某时间点数据缺失，则系统应按规则填补：短缺失（≤ 3 点）线性插值，长缺失标记为 gap 并降低该窗口置信度。 | S |
| FR-2.4 | 特征工程模块应定义清晰的输入输出契约（输入原始窗口 → 输出特征向量），本期实现基础特征子集，其余留扩展点。 | S |
| FR-2.5 | 系统应生成模型输入特征：滑动窗口水位统计、累计降雨（1h/3h/6h/12h）、雨强峰值、水位变化率、预见期降雨预报量、时间特征。 | S |
| FR-2.6 | 系统应支持多源数据的空间关联（雨量站 → 监测点映射关系可配置）。 | P |

### FR-3 水位预测（原型必跑通，模型占位）

| 编号 | 需求描述（EARS） | 优先级 |
|---|---|---|
| FR-3.1 | 当用户对某监测点发起预测请求并指定预见期（1/3/6/12 h）时，系统应返回该预见期内的水位预测序列、预测峰值、峰值时间与置信区间。 | M |
| FR-3.2 | 当系统处于运行状态时，应按配置周期（默认 5 min）对所有启用监测点自动执行滚动预测。 | S |
| FR-3.3 | 系统应记录每次预测的模型标识、模型版本与特征口径，保证结果可追溯。 | M |
| FR-3.4 | **系统应保存预测曲线的逐点明细（时间戳、预测值、置信上下界）至 `forecast_point` 表**，为后续精度评估预留数据基础。 | **M** |
| FR-3.5 | 若历史数据长度不足模型最小输入窗口，则系统应拒绝预测并返回错误码 DATA_NOT_ENOUGH。 | M |
| FR-3.6 | 若模型推理失败，则系统应降级返回最近一次有效预测并标注"数据延迟"。 | M |
| FR-3.7 | 系统应支持通过配置切换预测模型实现，切换不需修改业务代码。 | **M**（对应场景 S7） |
| FR-3.8 | 系统应至少提供两个可替换的模型实现（占位级），用于演示模型可插拔。 | M |
| FR-3.9 | 系统应对滚动预测结果做相邻窗口平滑，避免界面频繁跳变；原始模型输出与平滑后曲线应同时保存。 | S |
| FR-3.10 | 当 6h/12h 预见期被请求时，系统应将数值天气预报（NWP）降雨预报作为模型输入。 | P（依赖真实数据） |

> **FR-3.4 为什么仍是 M**：这不是功能优先级问题，是**数据模型正确性问题**。设计说明书的 Forecast 表只存 `peak_level`，但校准模块要求"预测 vs 实况对比算 RMSE"——没存逐点曲线就算不了，也无法回看当时的预测曲线。现在一次建对的代价极小，后期补的代价是重构存储层。

### FR-4 研判预警（原型层，逻辑完整）

| 编号 | 需求描述（EARS） | 优先级 |
|---|---|---|
| FR-4.1 | 当预测水位峰值达到某等级阈值时，系统应生成对应等级预警（蓝/黄/橙/红），并记录触发原因（峰值水位、对应阈值、预见期、触发时间）。 | M |
| FR-4.2 | 当预测水位持续超过阈值且持续时长达到配置值时，系统应将预警等级上调一级。 | S |
| FR-4.3 | 当同一监测点在配置时间窗（默认 30 min）内已存在同级或更高级的生效预警时，系统不应重复生成新预警，仅更新原有记录。 | M |
| FR-4.4 | 当预测峰值回落至阈值以下并持续配置时长（默认 15 min）时，系统应将该预警置为"已解除"并记录解除时间。 | S |
| FR-4.5 | 各级阈值应可按监测点独立配置，并支持运行时修改后立即生效于下一次研判。 | M |
| FR-4.6 | 若某监测点未配置阈值，则系统应使用全局默认阈值，并在预警原因中标注"使用默认阈值"。 | S |
| FR-4.7 | 系统应支持预警推送 webhook 预留（配置地址，命中即 POST）。 | P |

## 2.3 关键技术决策论证

### ADR-1R：预测模型 —— 本期不决策，用零依赖占位模型（替代 V1.0 的 ADR-1）

**V1.0 原决策及其问题**
V1.0 曾论证"Prophet 算法上不适合降雨驱动的水位预测，应改用 LightGBM"。该论证**技术上成立**（Prophet 建模的是"时间的函数"而非"降雨的函数"；每次预测需重新拟合 Stan，撑不住 5 分钟滚动预测），但**力气用错了地方**——本期不考核精度，为一个占位实现去争算法优劣没有意义。

**V1.1 新决策**：把问题从"哪个算法更好"换成"**哪个实现能让骨架稳稳跑起来**"。

按这个标准，Prophet 的问题变了，而且变成致命问题：

| 问题 | 性质 | 影响 |
|---|---|---|
| 依赖 `cmdstanpy`，需下载/编译 CmdStan | **安装工程风险** | Windows 下安装失败率高，`pip install` 可能直接失败 → **违反 NFR-1** |
| 模型文件与依赖体积大 | 交付负担 | 与"轻脚手架"目标冲突 |
| 每次预测需重新 fit（秒~十秒级） | 运行时风险 | 演示时点击"发起预测"要等，观感差 |

**结论：Prophet 连"占位"都不合适——它的风险不在算法，在装不装得上。**

**占位模型方案**（零额外依赖，纯 numpy/pandas 实现）：

| 模型 | 逻辑 | 用途 |
|---|---|---|
| **NaiveModel**（持久性模型） | `level(t+h) = level(t) + (base_level − level(t)) × decay × h` —— 当前水位向基准水位缓慢回落 | 兜底实现，验证环境是否正常；任何情况下都能跑 |
| **LinearResponseModel**（降雨线性响应） | `Δlevel(t+h) = Σᵢ wᵢ · rain(t−i) − k · (level(t) − base_level)` —— 历史降雨加权求和驱动水位上涨，同时向基准水位回落 | **主力演示模型**。形态体现"降雨驱动 + 汇流滞后 + 退水" |

**为什么占位模型也不能纯随机**：即使不考核精度，预测曲线的**形态合理性**直接决定演示能不能说服人。纯随机曲线一眼就假；LinearResponseModel 能表现出"下暴雨 → 水位滞后上涨 → 雨停后缓慢退水"的正确形态，而这恰恰是本系统要传达的核心业务规律。成本只有二十行代码。

**扩展点保留**（NFR-4）：

```
backend/app/algorithms/model/
├── base.py                    # ForecastModel 抽象接口（fit / predict）
├── naive_model.py             # ✅ 本期实现（占位）
├── linear_response_model.py   # ✅ 本期实现（占位）
├── lgbm_model.py              # 🟢 可选实现
├── prophet_model.py           # # EXT-POINT(MODEL): Prophet 实现位
└── tcn_model.py               # # EXT-POINT(MODEL): PyTorch TCN 实现位
```

**将来后悔成本极低**：`Model` 表的 `model_type` 枚举扩展 + 新增一个实现 `ForecastModel` 的类 + 配置文件加一项，业务层完全不动。这正是骨架要做到的。

### ADR-2：时序数据存储 —— 用 SQLite + 文件，不引入时序数据库

**先算账再选**：

```
本期模拟数据：10 监测点 × 5 min × 3 个月 ≈ 26 万行
即使放大到：  10 监测点 × 5 min × 1 年   ≈ 105 万行
远期：       100 监测点 × 1 min × 3 年   ≈ 1.58 亿行
```

**决策**：本期用 **SQLite 单文件（元数据 + 预测明细）+ Parquet/CSV 文件（水位降雨原始明细）**。105 万行对 SQLite 毫无压力（单表千万行以内常规查询均为毫秒级）。

**理由**：引入 IoTDB/TimescaleDB 意味着多一个容器、多一套连接配置、多一份运维，而本期数据量下收益为零，且直接违反 NFR-1。

**如何保证未来可替换**：所有时序读写收敛到 `TimeSeriesRepository` 接口，业务层不写具体引擎的 SQL。未来换 TimescaleDB（首选，PostgreSQL 生态、迁移成本最低）或 IoTDB（信创/国产化场景）只改实现类。

### ADR-3：模拟数据生成 —— 形态合理即可，与占位模型共用同一套参数

V1.0 曾建议实现完整简化水文模型（泊松降雨事件 + 产流 + 单位线 + 指数退水）。V1.1 依据定位澄清**简化**：不追求严格水文机理，但必须保证**形态合理**——即"下雨会涨水、涨水有滞后、雨停会退水"这条因果关系成立。

**实现建议（成本极低）**：让数据生成器与 `LinearResponseModel` **共用同一套响应参数**，递推生成历史序列：

```
level(t) = level(t−1) + Σᵢ wᵢ·rain(t−i) − k·(level(t−1) − base) + noise
```

**收益**：
1. 降雨与水位存在可见因果与滞后关系，演示时说得通；
2. 生成器内部参数是已知真值，需要时可直接作为精度评估的 ground truth；
3. 可注入极端降雨事件，一键制造"预警演示场景"（演示时很有用）；
4. 与占位模型共用代码，实现成本几乎为零。

### ADR-4：实时通信 —— 本期轮询，WebSocket 留占位

- **本期**：REST + 30 s 轮询。数据量小、实现简单、调试成本低。
- **占位约定**：`backend/app/api/ws.py` 保留空路由文件并标注 `# EXT-POINT(INTEGRATION): WebSocket 推送`。
- **将来引入时的建议**：用**单条 WebSocket `/ws` + `type` 字段路由**（`level | prediction | alert | status`），**不要按原设计做 4 条独立物理连接**——4 条连接使连接数翻 4 倍，且各自维护心跳重连易出现"水位在推但预警断了"的不一致。

| NFR-9 接口规范 | 统一 `/api/v1` + `{code,message,data}` + 错误码表 | ✅ |

## 2.6 与原始方案的差异汇总

| # | 原方案 | V1.1 方案 | 差异级别 | 影响面 |
|---|---|---|---|---|
| D1 | Prophet 作预测主基线 | **本期不决策**；零依赖占位模型（Naive + LinearResponse），Prophet/LightGBM 留实现位 | 重大 | 后端 model 模块、依赖清单 |
| D2 | 时序数据库（待定） | 本期 SQLite + Parquet；生产阶段 TimescaleDB / IoTDB | 重大 | 后端 database 层、部署 |
| D3 | 4 条独立 WebSocket | 本期轮询；将来单连接 + type 路由 | 中等 | 前端、后端 ws 层 |
| D4 | Forecast 表仅存 peak_level | 新增 `forecast_point` 逐点明细表 | 中等（**不补则将来无法评估**） | 数据库设计 |
| D5 | 指标仅 RMSE/MAE | 数据模型中预留峰值误差/峰值时间误差/POD/FAR/CSI 计算口径（本期不实现） | 轻微 | 校准模块、验收标准 |
| D6 | 模拟数据为"趋势+噪声" | 共用 LinearResponse 参数的形态合理生成器 | 轻微 | 后端 data 模块 |
| D7 | 立即 Docker 部署 | 本期脚本启动，Docker 后置 M5 | 轻微 | 部署计划 |
| D8 | 前端 Pinia | 本期不引入 | 轻微 | 前端 |
| D9 | 前后端强耦合 | 前端 mock 双通道，可独立开发 | 轻微（新增） | 前端 |

**相比 V1.0 的关键变化**：D1 从"必须换 LightGBM"改为"**本期不装任何有安装风险的模型**"。这不是技术判断的回退，而是把决策依据从"算法优劣"换成"脚手架能不能跑起来"之后的必然结果。
