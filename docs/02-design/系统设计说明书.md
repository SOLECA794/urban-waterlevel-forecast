## 文档说明

本文档根据城市内涝（积水）预测预警系统的既定功能需求进行设计。核心技术路线确定为 **Vue 3 + TypeScript 前端、FastAPI Python 后端、SQLite + Parquet + DuckDB 存储、零依赖占位预测模型**，并采用**模块化单体 + 端口适配器**架构，为后续演进为 Agent 项目预留接入位。

本版依据《需求分析与技术选型》V1.1、《架构升级与 Agent 预留设计》V1.2、《需求覆盖核对与缺口补齐》V1.3、《后端规划书》V2.1、《前端规划书》V2.0 定稿，替代 V1.0（V1.0 中 Prophet/PyTorch、时序数据库、多路 WebSocket 等方案已被下述决策取代）。

## 1 引言

### 1.1 编写目的

本文档用于系统性描述城市内涝（积水）预测预警系统的总体结构、功能划分、技术实现、性能约束、数据模型以及前后端接口。文档既作为开发阶段的统一设计依据，也作为数据源、算法、前端、后端协同工作的接口约束。

系统目标是建立从"多源数据接入—数据治理—预测编排—协同修正—阈值研判—预警发布—模型校准"的完整闭环，使未来 1h / 3h / 6h / 12h 的水位预测结果能够在统一平台中完成计算、展示与管理。

**本期交付定位：脚手架 + 可运行原型。** 不考核模型实际精度，目标是"把项目骨架、前端原型、后端留白接口搭起来，数据用模拟的"。评判标准从"算法优劣"变为"结构完整、接口清晰、可持续填充"。

本文档重点解决以下问题：

- 定义 Vue 3 + TypeScript、FastAPI、SQLite/Parquet/DuckDB、占位模型、Agent 预留五个核心技术组件的职责边界和数据流。
- 规范模块化单体 + 端口适配器架构下，应用层/领域层只依赖 Port（抽象接口）、不依赖具体 Adapter 的铁律。
- 明确"预测 → 协同修正 → 研判 → 预警"的实时业务链路，以及前端轮询刷新与 SSE 预留的演进路径。
- 明确监测点、水位时序、预测明细、编排决策、预警记录、模型版本、Agent 会话的可追溯存储方式。
- 给出数据库表、REST API、错误码和关键交互序列，为直接编码实现提供依据。

### 1.2 项目背景

城市内涝是城市高频、高损失灾害，治理方向正从"事后处置"转向"事前预报预警"。本系统面向城市防汛场景，通过融合降雨实况、气象预报、雷达、水位监测等多源数据，预测未来水位并输出分级预警，为防汛值班人员提供决策依据。

项目构建一套面向训练和在线使用的 Web 系统。系统既要支持监测点水位数据的实时接入与展示，也要支持多预见期水位预测、阈值研判预警、预测结果对比与模型定期校准。

原型阶段优先考虑可部署性和演示稳定性，采用单机 B/S 架构：数据源接入实验电脑或模拟生成，FastAPI 与预测模型运行在本机，Vue 3 前端通过浏览器访问本机服务。该模式减少外部网络依赖，能够在不引入复杂分布式组件的情况下完成在线闭环演示。

| 设计目标 | 说明 |
|---|---|
| 实时性 | 持续接入水位/降雨数据，以低延迟向前端展示水位、预测与预警状态（轮询 ≤ 30s）。 |
| 完整性 | 覆盖数据接入、治理、预测、协同修正、研判、预警、校准、记录、Agent 预留九类核心业务。 |
| 可追溯性 | 任何监测点、水位序列、预测结果、编排决策、预警和模型均可通过数据库关系追踪。 |
| 易部署 | 原型版本可在一台 Windows / Linux 电脑上运行，`pip install` 一次成功，一条命令启动。 |
| 可扩展 | 后续可替换数据源、升级预测模型、接入 Agent、增加预见期或拆分独立推理服务，不改业务层代码。 |

## 2 系统总体设计

### 2.1 整体架构

系统采用**模块化单体 + 端口与适配器（六边形架构）**。物理上单进程（一条命令启动、零运维），逻辑上按领域切分，模块间只通过接口（Port）通信，不直接互相 import 实现。

分层结构：

```
┌─────────────────────────────────────────────────────┐
│  接入层   API(REST /api/v1) · SSE(流式，预留) · MCP(占位)│
├─────────────────────────────────────────────────────┤
│  应用层   ForecastService · AlertService ·            │
│           ForecastRevisionService · AgentService      │
├─────────────────────────────────────────────────────┤
│  领域层   实体 + Port（抽象接口）                       │
│           DataSource / ForecastModel / Tool / Agent   │
│           ForecastOrchestrator（Agent-A）             │
├─────────────────────────────────────────────────────┤
│  基础设施层  各 Port 的具体实现（Adapter）              │
│           SimulatedSource / NaiveModel / LinearResp / │
│           SQLiteRepo / ParquetStore / DuckDBAnalytics /│
│           ToolRegistry / EchoAgent                    │
└─────────────────────────────────────────────────────┘
```

**铁律**：应用层与领域层**不得 import 任何具体 Adapter**，只依赖 Port。这条保证了可替换性，也是 `grep EXT-POINT` 能穷尽所有待填点的前提。

**为什么不是微服务**：对本项目（单机 demo、后续演进为 Agent 应用），微服务带来的分布式复杂度远超收益。模块化单体在"逻辑上可拆分"与"物理上可单跑"之间取得平衡——将来若某模块需要独立部署，只需把该模块的实现替换成远程调用适配器，业务层代码不动。

系统内部同时存在两类数据链路：第一类是低频业务链路，如查询监测点、创建预测任务、查询记录、触发模型校准等，统一通过 REST API 完成；第二类是高频展示链路，如实时水位、预测结果、预警状态，本期采用前端轮询（30s）刷新，SSE 预留为后续 Agent 流式输出与预警事件推送。

### 2.2 整体功能架构

系统功能围绕"接入—治理—预测—修正—研判—预警—校准—记录—Agent"闭环展开，共划分为九个一级模块。

| 模块 | 核心功能 | 主要输入 | 主要输出 |
|---|---|---|---|
| 数据接入 | 数据源连接、定时采集、状态监控（模拟/真实） | 数据源配置、采集计划 | 连接状态、数据流（实况+预报两路） |
| 数据治理 | 清洗、时空对齐、缺失填补、特征工程 | 原始多源数据 | 规整后的特征序列 |
| 水位预测 | 多预见期水位预测（1h/3h/6h/12h） | 特征序列、预测模型 | 预测曲线、置信区间 |
| 预测编排（Agent-A） | 模型自适应选择、多源融合权重、修正策略、置信区间自适应、降级决策 | 预测上下文（数据状态、近期误差） | 编排决策（可追溯） |
| 多源协同修正 | 滚动校正（结合实时监测、最新预报、已发生事件） | 新息（实测/预报/事件）、原始预测 | 修正后预测曲线与置信区间 |
| 研判预警 | 阈值判定、趋势参考、等级输出、生命周期 | 修正后预测结果、阈值配置 | 预警等级、触发原因 |
| 可视化应用 | 总览、监测点详情、预警中心、设置、Agent 控制台 | 预测/预警数据 | 图表、大屏、交互 |
| 交互智能体（Agent-B） | 会话编排、工具调用（占位） | 用户问题 | 回答、工具调用轨迹 |
| 模型校准 | 参数校准（做实）、重训（占位）、在线适应（预测级） | 历史预测、实测数据 | 校准参数、性能对比 |

### 2.3 整体技术架构

#### 2.3.1 技术栈总览

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 | Python 3.11 | 锁版本，避免 3.12+ 部分科学计算包 wheel 不稳 |
| Web 框架 | FastAPI + Uvicorn + Pydantic v2 + Pydantic Settings | 自带 OpenAPI、异步、依赖注入 |
| ORM/迁移 | SQLAlchemy 2.0 + Alembic | 数据库演进有版本管理 |
| 业务存储 | SQLite 单文件 | 元数据、预警、预测明细 |
| 明细存储 | Parquet（pyarrow） | 水位/降雨原始序列 |
| 分析查询 | DuckDB | 直接读 Parquet，零服务，覆盖将来 Agent 聚合分析 |
| 数据处理 | pandas + numpy | 重采样、插值、特征工程 |
| 任务调度 | APScheduler + 任务表 | 滚动预测；长任务可查询状态（CPU 密集作业投线程池，避免阻塞事件循环） |
| 日志 | structlog（JSON 结构化） | trace_id / session_id 贯穿 |
| 预测模型 | NaiveModel + LinearResponseModel | 纯 numpy 占位；接口与真模型完全一致 |
| Agent | ToolRegistry（做实）+ EchoAgent（占位）+ Agent-A 规则编排 | 见 §3.4 / §3.8 |
| 前端 | Vue 3 + TypeScript + Vite + Element Plus + ECharts + Pinia + VueUse | OpenAPI 自动生成 TS 类型 |
| 实时 | REST + 轮询（30s） | SSE 预留 |
| 部署 | venv + 一键脚本 | Docker Compose 后置 M5 可选 |

**明确不引入**（含理由）：prophet（cmdstanpy 安装失败风险，违反 NFR-1）、torch（体积 >2GB，本期无 GPU 需求）、celery/redis（分布式组件，单机不需要）、时序数据库集群（数据量下收益为零且引入运维负担）、向量数据库（Agent 知识库阶段再评估）。

#### 2.3.2 前端逻辑分层

Vue 3 前端按照页面层、组件层、状态层、API 层和基础设施层组织。页面不直接处理原始协议，而是通过统一 client（解包 `{code,message,data}`）与后端通信。API 类型由 OpenAPI 自动生成（`npm run gen:api`），保证前后端契约单一事实来源。

```
frontend/
├─ src/
│  ├─ pages/          # Overview、StationDetail、AlertCenter、Settings、AgentConsole(占位)
│  ├─ components/     # StationCard、TrendChart、AlertBadge、AlertList、ForecastSummary、DegradedBanner、ToolCallTrace
│  ├─ stores/         # useStationStore、useAlertStore、useSystemStore、useAgentStore(Pinia)
│  ├─ api/            # client.ts（统一解包）、schema.d.ts（自动生成，勿手改）、endpoints.ts
│  ├─ composables/    # usePolling、useSSE(预留)、useEcharts
│  ├─ mock/           # fixtures（stations/series/forecast/alerts/agent），VITE_USE_MOCK 切换
│  ├─ router/         # 四页面 + /agent
│  └─ utils/
└─ package.json
```

前端必须能在后端未启动时独立开发与演示（`VITE_USE_MOCK=true` 走 mock，`false` 走真实接口，两套数据形状一致，切换只改环境变量）。

#### 2.3.3 后端逻辑分层

FastAPI 后端按照接入层（api）、应用层（application）、领域层（domain）、基础设施层（infrastructure）组织。路由只负责参数验证和返回封装，具体业务进入应用层；数据源适配、预测模型、工具注册表和数据库访问均通过领域层 Port 隔离。

```
backend/
├─ app/
│  ├─ main.py                     # FastAPI 入口 + lifespan
│  ├─ core/                       # config、logging、errors、response、deps
│  ├─ domain/
│  │  ├─ models/                  # 领域实体
│  │  └─ ports/                   # data_source / forecast_model / repository / tool / agent / orchestrator
│  ├─ application/                # forecast_service / alert_service / station_service / calibration_service / agent_service / revision_service
│  ├─ infrastructure/
│  │  ├─ datasource/              # simulated_source ✅ / real_source_adapter 🔶
│  │  ├─ forecast/                # naive_model ✅ / linear_response ✅ / lgbm_model 🔶
│  │  ├─ persistence/             # sqlite_repo / parquet_store / duckdb_analytics
│  │  ├─ agent/                   # tool_registry ✅ / tools/ / echo_agent 🔶
│  │  └─ scheduler/
│  ├─ api/                        # v1 / sse(预留) / mcp(占位)
│  └─ schemas/                    # Pydantic 请求/响应契约
├─ migrations/                    # Alembic
├─ config/                        # default.yaml + stations.yaml
├─ scripts/                       # generate_demo_data.py、dev.ps1/dev.sh
├─ tests/
├─ requirements.txt
└─ README.md
```

### 2.4 设计约束与原则

**本期交付分三层，三层的验收标准不同：**

| 层 | 内容 | 验收标准 | 典型例子 |
|---|---|---|---|
| **骨架层**（必须做实） | 目录结构、模块边界、接口契约、数据模型、配置外置、异常处理框架、日志 | 结构合理、职责单一、扩展点明确 | `DataSource` 抽象 + `SimulatedSource`；统一响应 `{code,message,data}` |
| **原型层**（形态到位，逻辑可简） | 五个前端页面、全部 REST 接口、"预测→修正→预警"演示链路 | UI 元素完整、接口返回符合契约、演示跑得通 | 详情页历史+预测+阈值线全画出，预测值由占位模型给出 |
| **占位层**（留白） | 真实数据源、真实预测算法、重训、推送、Agent 推理 | **有接口定义 + 有占位实现 + 有扩展点标注** | `RealSourceAdapter` 只有签名与 TODO；`/api/v1/calibrations` 返回 `pending` |

**核心原则：**

1. **占位 ≠ 缺失**。每一处留白都必须是"看得见形状的空位"：接口签名完整、能返回符合契约的假数据、并明确标注将来替换成什么。评审时要能一眼看出"这里将来填什么、怎么填"。
2. **依赖极简**。任何存在安装失败风险的依赖一律不进 `requirements.txt`。一条命令跑不起来，骨架就是失败的。
3. **前后端可独立启动**。前端靠 mock 能独立跑完五个页面，后端靠占位模型能独立返回全部接口，两边互不阻塞。
4. **配置驱动一切**。数据源类型、模型类型、点位、阈值、预见期全部外置。将来接真实数据、升级真实模型，是"改配置 + 填一个实现类"，不是"改结构"。
5. **留白统一标注**。全项目统一使用 `# EXT-POINT(类型): 说明` 标记，类型限定 `DATASOURCE` / `MODEL` / `ALGORITHM` / `INTEGRATION` / `AGENT`。执行 `grep -rn "EXT-POINT" backend/` 即可列出全部待填位点。
6. **Agent 能力边界**。能力分级 L0/L1/L2，L2 变更必须人工确认，**L3（自动执行）永不做**——防汛预警的发布责任必须由人承担。
7. **接口规范**。REST 统一 `/api/v1` 前缀；响应统一 `{code, message, data}`；前端禁止仅凭 HTTP 200 判定业务成功。

## 3 系统功能模块详细设计

本章从实际开发角度对各业务模块进行详细设计。所有预测与预警操作均绑定当前 Station 与预测任务；需要形成可评分数据的功能必须在数据库中保留元数据，并将预测结果与实际水位建立稳定对应关系。

### 3.1 数据接入模块

数据源模块通过 `DataSource` Port 屏蔽不同数据源差异，向上层提供统一接口。原型阶段支持模拟数据源，真实数据源通过配置切换。

| 子功能 | 设计说明 |
|---|---|
| 数据源选择 | 读取可用数据源及基本信息；原型阶段支持模拟数据源，真实数据源（`RealSourceAdapter`）通过配置切换，实现留占位。 |
| 连接/断开 | 连接成功后初始化采样间隔、点位列表、缓冲区和数据源状态。 |
| 数据采集 | 采集任务持续获取数据块并写入线程安全队列或 Ring Buffer。 |
| 状态监控 | 对超时、异常幅值、点位无数据进行状态提示；连续 3 个采样周期无数据置 ERROR 并暂停预测，恢复后自动重连。 |

数据源运行状态定义为 DISCONNECTED、CONNECTING、READY、STREAMING、ERROR 五种。预测业务只有在 READY 或 STREAMING 状态下才允许启动。

**模拟数据源双路输出（V1.3）**：模拟源同时产出两路降雨数据——实况降雨 `rain_observed(t)` 与降雨预报 `rain_forecast(t_issue, h)`（在 t_issue 时刻对未来 h 小时的预报）。预报误差建模体现"预见期越长越不准"：

```
rain_forecast(t, h) = rain_true(t+h)·(1 + ε(h))
ε(h) ~ N(bias(h), σ(h))，σ(h) 与 |bias(h)| 随 h 单调增大
```

可额外加入对峰值的系统性低估（真实数值预报对强对流的典型缺陷），让演示更真实。由此 6h/12h 从"占位"升级为"本期跑通"；将来接真实 NWP 时只需替换 `rain_forecast` 的取数实现。

### 3.2 数据治理模块

数据治理负责将多源原始数据转化为模型可用特征序列：

| 子功能 | 设计说明 |
|---|---|
| 数据清洗 | 剔除异常值（超物理范围、跳变），处理传感器故障标记。 |
| 时空对齐 | 统一时间粒度（默认 5 min）与空间网格，多源数据按时间戳外连接对齐。 |
| 缺失填补 | 短缺失（≤ 3 点）线性插值，长缺失标记 gap 并降低该窗口置信度。 |
| 特征工程 | 生成滑动窗口水位统计、累计降雨（1h/3h/6h/12h）、雨强峰值、水位变化率、预见期降雨预报量、时间特征（小时/季节）。 |

特征工程为**独立模块**：输入 DataFrame、输出 DataFrame，契约清晰、可单测——这是将来接真模型时唯一需要扩展的地方。

### 3.3 水位预测引擎模块

预测引擎是系统核心，负责输出未来 1h / 3h / 6h / 12h 的水位预测。模型统一通过 `ForecastModel` Port 访问，输入为多变量特征窗口，输出为预测水位序列、峰值、峰值时间与置信区间。

```
输入：FeatureWindow -> [features × window_len]
输出：ForecastResult -> points[]（t/level/lower/upper）、peak_level、peak_time、
                        confidence_interval、model_id、inference_ms
```

`ForecastResult` 结构与将来真模型**完全一致**。

**占位模型**（零额外依赖，纯 numpy/pandas 实现）：

| 模型 | 逻辑 | 用途 |
|---|---|---|
| **NaiveModel**（持久性） | `level(t+h) = level(t) + (base_level − level(t)) × decay × h` | 兜底实现，验证环境正常；任何情况下都能跑 |
| **LinearResponseModel**（降雨线性响应） | `Δlevel(t+h) = Σᵢ wᵢ·rain(t−i) − k·(level(t) − base_level)` | **主力演示模型**，体现"降雨驱动 + 汇流滞后 + 退水" |

两个模型并存即支撑场景 **S7「模型可插拔演示」**：切换模型，预测曲线变化，业务代码不动。占位模型不纯随机——预测曲线的**形态合理性**直接决定演示能不能说服人。

**多预见期**：短预见期（1h/3h）以历史水位 + 实时降雨 + 短临降水预报输入；中长预见期（6h/12h）**强制启用降雨预报序列输入**（Agent-A 决策 D1）。

**平滑**：结果层采用滚动预测 + 相邻窗口平滑（指数平滑或最近 N 窗均值）。原始模型输出（`pred_level_raw`）与修正后输出（`pred_level`）同时保存，方便离线分析（FR-3.7/FR-3.9）。

**调度**：APScheduler 按配置周期（默认 5 min）对所有启用监测点自动执行滚动预测；CPU 密集计算投放到线程池执行，避免阻塞 FastAPI 事件循环。

### 3.4 预测编排智能体（Agent-A）

需求书"时序预测模型 + AI 算法 + **智能体**"中的"智能体"，语义是**模型具备自适应与自融合能力**。本模块在每次预测前做出五项决策，全部记录、全部可解释：

| # | 决策 | 输入依据 | 本期规则（示例） |
|---|---|---|---|
| D1 | **模型自适应选择** | 预见期、数据充足度、各模型近期误差 | 数据不足 → NaiveModel；否则 LinearResponseModel；6h/12h 强制启用预报输入 |
| D2 | **多源融合权重** | 各源质量（延迟、缺失率、近期偏差） | `w ∝ 1/(1 + 近期偏差)`，归一化 |
| D3 | **修正策略** | 当前新息大小、数据新鲜度 | 新息 > 阈值 → 启用修正，`α = 0.6` |
| D4 | **置信区间自适应** | 近期误差、预见期长度 | `宽度 ∝ 近期RMSE × √h` |
| D5 | **降级决策** | 数据源状态 | 断流 → NaiveModel + 标注"数据延迟" |

**实现**：`ForecastOrchestrator` Port，本期 `RuleBasedOrchestrator` 纯 Python 规则，零依赖、无需 LLM、无需联网。将来可升级为 bandit/RL 选模型或 LLM 生成策略，实现替换不改调用方。

**决策可追溯**：每次预测的决策写入 `forecast_decision` 表（selected_model、fusion_weights、revision_alpha、ci_scale、degraded、reason）。这张表同时服务三件事：预测结果可复现可解释（NFR-10）；Agent-B 的 `explain_forecast` 工具直接读它（两层 Agent 在此打通）；演示时可直接展示"系统为什么选了这个模型"。

### 3.5 多源协同修正模块

需求书原文："多源协同修正：滚动校正（结合实时监测、最新预报、已发生事件）"。**"滚动预测"（重新算一遍）不等于"滚动校正"（用已发生的事实修正尚未发生的预测）**，本模块补齐显式设计。

**三类触发：**

| 触发 | 对应需求书措辞 | 说明 |
|---|---|---|
| T1 | 实时监测 | 新的水位/雨量实测到达 |
| T2 | 最新预报 | 降雨预报刷新 |
| T3 | 已发生事件 | 进入退水期 / 已记录内涝事件 |

**算法：多源加权新息 + 时间衰减**

```
# 1) 各源新息（最近预测错了多少）
e_level = actual_level(t_now) − predicted_level(t_now)
e_rain  = Σ(actual_rain − predicted_rain)             # 最近窗口
e_fcst  = 最新预报量 − 上一版预报量

# 2) 多源加权合成（权重来自 Agent-A 的 D2 融合权重——"多源协同"的字面实现）
e = w_level·e_level + w_rain·e_rain + w_fcst·e_fcst

# 3) 对未发生时段做衰减修正
corrected(t) = predicted(t) + α·e·ρ^(Δt)              # Δt = t − t_now > 0
#    α 修正强度（Agent-A D3 决策，默认 0.6）
#    ρ 时间衰减（默认 0.85/步）：越远的未来修正越少

# 4) 置信区间随预见期展宽
width(t) = width_raw(t)·(1 + β·Δt)
```

**存储**：修正量写入 `forecast_point.revision`，模型原始输出保留在 `pred_level_raw`，对外输出值 `pred_level = pred_level_raw + revision`。

**演示价值**：详情页同时画原始预测（细虚线）、修正后预测（粗虚线）、实测（实线），修正效果一眼可见——这是"多源协同修正"最好的证明方式。

### 3.6 研判预警模块

研判预警模块根据**修正后预测水位曲线**输出分级预警：

| 子功能 | 设计说明 |
|---|---|
| 阈值判定 | 预测峰值 / 持续时间与阈值比较，映射为蓝/黄/橙/红四级。 |
| 趋势参考 | 结合预测曲线上升趋势与累计降雨，辅助升级判断。 |
| 阈值配置 | 阈值按监测点可配置（配置文件/界面维护），演示时可动态调整，运行时修改立即生效。 |
| 预警生成 | 输出预警等级、触发原因（峰值水位、对应阈值、预见期、触发时间）与建议行动。 |
| 生命周期 | 去重（30 min 内同级/更高级生效预警不重复生成）、解除（峰值回落超 15 min 置 resolved）、记录解除时间。 |
| 预警提前量 | 记录 `lead_minutes_advantage` = 阈值报警触发时刻 − 系统预警触发时刻，作为演示亮点。 |
| **参考级降权（V1.3）** | 6h/12h 长预见期生成的预警标记 `is_reference = 1`（参考级），界面浅色区分、不计入有效预警统计、默认不推送——避免长预见期不确定性造成误报风暴。 |

预警生成基于修正后预测值：修正生效后，若原预测越阈值、修正后回落，则不生成预警；反之亦然。

### 3.7 可视化应用模块

可视化应用层承担系统人机交互：总览页展示监测点卡片列表与预警状态；详情页展示历史水位、预测曲线（原始 vs 修正）、阈值线与预见期切换；预警中心展示预警记录、等级与处置状态；系统设置维护点位/阈值/数据源/模型；Agent 控制台展示工具调用链路（占位）。详见第 6 章 UI 设计。

### 3.8 交互智能体（Agent-B）与工具层

**Agent-B 是对话式交互智能体**（对应需求书"智能体（辅助决策）"），与 Agent-A 是两层不同语义，通过 `forecast_decision` 表与 `explain_forecast` 工具打通。

**Tool 抽象（本期做实）**：

```python
class Tool(Protocol):
    name: str
    description: str                    # 给 LLM 看的用途说明
    parameters: dict                    # JSON Schema
    risk_level: Literal["L0","L1","L2"]
    async def execute(self, **kwargs) -> ToolResult
```

`ToolRegistry` 提供 `register` / `list` / `get` / `invoke`（含 risk_level 运行时强制校验，L2 无人工确认令牌则拒绝执行）。

| 工具 | 风险级 | 说明 | 本期 |
|---|---|---|---|
| `list_stations` | L0 | 列出监测点与当前状态 | ✅ |
| `get_station_status` | L0 | 查询单点位详情与预警状态 | ✅ |
| `get_level_series` | L0 | 查询历史水位/降雨序列 | ✅ |
| `run_forecast` | L0 | 对某点位发起预测 | ✅ |
| `get_active_alerts` | L0 | 查询生效预警列表 | ✅ |
| `explain_alert` | L1 | 解释某条预警的成因 | ✅ |
| `explain_forecast` | L1 | 解释 Agent-A 的编排决策 | ✅ V1.3 |

| `draft_alert_report` | L1 | 生成预警报告草稿 | 🔶 |
| `search_similar_events` | L1 | 检索历史相似内涝事件 | 🔶 |

**能力分级与 Human-in-the-loop：**

| 级别 | 能力 | 是否需要人工确认 | 本期 |
|---|---|---|---|
| L0 | 只读查询 | 否 | ✅ 开放 |
| L1 | 生成内容（报告、解读、建议） | 否（产物仅供人参考） | ✅ 开放 |
| L2 | 建议变更（阈值、配置） | **是，必须确认** | ✅ 开放"建议"，执行需确认 |
| L3 | 自动执行（发布预警、推送、改配置） | — | ❌ **永不做** |

> **L3 永久不做**是系统设计约束。防汛预警的发布责任必须由人承担，Agent 自动发布一旦误报或漏报无法追责。这一条在答辩时是加分项。

**Agent 会话占位**：`Agent` Port 定义 `chat(session_id, message) -> AsyncIterator[AgentEvent]`。本期 `EchoAgent` 接收消息 → 用关键词匹配选中 Tool → 执行 → 把结果包装成回答。**即使没有 LLM，也能演示完整的"提问 → 选工具 → 执行 → 回答"链路**。

**MCP 预留**：`api/mcp/` 下留路由与 `EXT-POINT(INTEGRATION)` 标注。任何支持 MCP 的客户端都能直接调用本系统能力，系统不绑定任何一家 Agent 框架。

**Agent 三表**：`agent_session` / `agent_message` / `agent_tool_call` 本期建结构、功能占位。`agent_tool_call` 天然成为系统操作的审计日志，对防汛业务有独立价值。

### 3.9 模型校准模块

需求书"模型校准"拆三项，各有明确落点：

| 子项 | 本期落点 | 说明 |
|---|---|---|
| **参数校准** | ✅ **做实** | 网格/随机搜索标定 `LinearResponseModel` 的降雨响应权重 `wᵢ` 与退水系数 `k`（纯 numpy，几十个参数，秒级完成）；提供 `calibrate_params` 工具（L1 级），演示时可现场跑一次参数标定，展示前后误差变化 |

| 异常类型 | 处理策略 |
|---|---|

## 4 数据库设计

系统采用"SQLite（业务元数据 + 预测明细）+ Parquet 文件（水位降雨原始序列）+ DuckDB（分析查询）"的混合存储方案。连续时序数据不直接写入 SQLite，而是以 Parquet 文件保存；SQLite 保存监测点、预测任务、编排决策、预警记录、模型、事件与 Agent 记录等核心信息。所有表由 Alembic 管理迁移。

### 4.1 数据设计原则

数据库设计遵循"结构简单、关系明确、便于追踪"的原则，以 Station 作为监测点核心实体，通过外键建立 Station、Forecast、Alert、Model、FloodEvent 之间的关联。水位时序数据按 station_id 定位，无需冗余存储点位信息。

**两个"现在不计算、将来必须算"的字段本期必须建好**：`forecast_point.actual_level`（事后回填，支撑精度评估）与 `alert.lead_minutes_advantage`（预警提前量）。现在建对的代价极小，后期补的代价是重构存储层。

### 4.2 实体关系设计

核心实体：Station（监测点）、Forecast（预测主记录）、ForecastPoint（预测逐点明细）、ForecastDecision（编排决策）、Alert（预警记录）、Model（模型版本）、FloodEvent（内涝事件）、Task（长任务）、AgentSession/AgentMessage/AgentToolCall（Agent 三表）。

```
Source 1 ──< Station 1 ──< Forecast >── 1 Model
                       │     │
                       │     ├──< ForecastPoint（逐点明细，1:N）
                       │     └──< ForecastDecision（编排决策，1:1）
                       └──< Alert >── 1 FloodEvent（事件归档）
Task（长任务状态） · AgentSession/Message/ToolCall（Agent 预留）
```

水位序列（Series）不设独立元数据表，按 station_id + 时间范围在 Parquet 中查询；历史预测与实测对比通过 ForecastPoint 表关联。

### 5.2 实时通信设计

**本期：REST + 30s 轮询。** 数据量小、实现简单、调试成本低，满足 NFR-7（刷新延迟 ≤ 30s）。

**SSE 预留**（Agent 流式输出与预警事件推送）：`backend/app/api/sse/` 保留路由并标注 `# EXT-POINT(INTEGRATION): SSE 推送`；`GET /api/v1/stream/alerts` 预留。前端 `useSSE` composable 预留，不可用时降级为普通请求。

**为什么 SSE 优先于 WebSocket**：

| 维度 | SSE | WebSocket |
|---|---|---|
| 方向 | 服务端→客户端（单向） | 双向 |
| 实现复杂度 | 低（就是 HTTP） | 高（握手、心跳、重连） |
| 自动重连 | 浏览器原生支持 | 需自行实现 |
| 穿透代理/网关 | 好 | 常被网关掐断 |
| 适用场景 | **LLM token 流、事件推送** | 高频双向交互 |

Agent 流式输出与预警事件推送 → SSE；实时水位高频波形（若将来做）才考虑 WebSocket。**不采用 V1.0 的 4 条独立 WebSocket 设计**——4 条连接使连接数翻 4 倍，且各自维护心跳重连易出现"水位在推但预警断了"的不一致。

### 5.3 数据源接口

```python
class DataSource(Protocol):
    async def connect(self, config: dict) -> SourceInfo: ...
    async def disconnect(self) -> bool: ...
    async def start_stream(self, sink: Callable[[DataBlock], Awaitable[None]]) -> bool: ...
    async def stop_stream(self) -> bool: ...
    async def get_status(self) -> SourceStatus: ...
    async def get_series(self, station_id: int, hours: int) -> pd.DataFrame: ...
```

具体数据源通过 Adapter 实现上述接口。业务层只依赖抽象数据源接口，避免将具体采集协议散落在 FastAPI 路由中。`SimulatedSource` 本期实现（含实况 + 预报双路输出），`RealSourceAdapter` 留签名与 EXT-POINT。

### 5.5 关键交互序列

**实时预测序列**：前端进入详情页 → 选择预见期并点击"发起预测"（REST POST predict）→ 后端 Agent-A 决策（写 forecast_decision）→ 占位模型推理 → 协同修正服务对新息做衰减修正（写 forecast_point.revision）→ 返回预测曲线（含 raw/修正后/置信区间）→ 前端图表绘制；预测峰值超阈值 → 研判模块生成预警（含 is_reference 与 lead_minutes_advantage）→ 预警中心轮询刷新。

**滚动修正序列**：模拟源到达新实测/新预报（T1/T2 触发）→ 协同修正服务计算各源新息 → Agent-A 给出融合权重与修正强度 → 对未发生时段做衰减修正 → 更新 forecast_point.revision 与置信区间 → 前端下一次轮询看到修正后的曲线。

**模型切换（S7）**：设置页切换模型 → POST /models/{id}/activate → 重新发起预测 → 同一接口返回不同模型的预测曲线 → 业务代码未改动。

**Agent 链路（演示）**：Agent 控制台提问 → EchoAgent 关键词匹配选中 Tool → ToolRegistry 执行（risk_level 校验）→ 返回结果包装成回答 + 工具调用轨迹（agent_tool_call 落库）→ 前端展示轨迹面板。

**参数校准序列**：设置页发起参数校准 → POST /models/{id}/calibrate-params → 网格/随机搜索标定 wᵢ/k → 返回前后误差对比 → 前端展示校准效果。

### 5.6 错误码与接口约束

| 错误码 | 名称 | 场景 | 处理建议 |
|---|---|---|---|
| 0 | OK | 请求成功 | 正常处理 |
| 1001 | SOURCE_NOT_CONNECTED | 数据源未连接启动预测 | 提示连接数据源 |
| 1002 | SOURCE_STREAM_ERROR | 数据源流异常/超时 | 暂停预测并重连 |
| 1101 | STATION_STATE_INVALID | 监测点状态不允许当前操作 | 刷新状态后重试 |
| 1201 | MODEL_NOT_READY | 模型未加载或不存在 | 选择有效模型 |
| 1202 | MODEL_INPUT_MISMATCH | 特征/窗口与模型不匹配 | 按模型配置调整 |
| 1301 | DATA_NOT_ENOUGH | 历史数据不足 | 继续积累数据 |
| 1401 | DATABASE_ERROR | 数据库写入失败 | 记录日志并执行补偿 |
| 1601 | TOOL_NOT_FOUND | Agent 调用了不存在的工具 | 检查工具名 |
| 1602 | TOOL_CONFIRM_REQUIRED | L2 工具缺少人工确认令牌 | 先确认再执行 |

所有 REST 响应统一采用 {code, message, data} 结构。HTTP 状态码用于表达网络/协议层结果，业务 code 用于表达数据源、预测、模型等应用状态。**前端禁止仅根据 HTTP 200 判断业务成功。**

### 5.7 系统总体运行流程

1. 启动后端 → 初始化数据源连接（READY/STREAMING）与模型加载
2. 数据接入任务持续采集并写入缓冲区（实况 + 预报双路）
3. 数据治理任务按时序滚动生成特征窗口
4. 预测任务按调度周期执行多预见期预测：Agent-A 决策 → 模型推理 → 协同修正 → 写入 Forecast/ForecastPoint/ForecastDecision
5. 研判模块对比阈值（基于修正后预测），命中则生成 Alert（含提前量/参考级）并记录
6. 前端轮询展示实时水位、预测曲线（原始 vs 修正）、预警状态
7. 校准任务：参数校准做实；重训占位返回 pending；在线适应由协同修正承担

### 5.8 接口版本与兼容策略

所有 REST 路径统一置于 `/api/v1` 下，通过子路径区分数据类型，为后续不兼容升级留位。模型版本、预处理配置和输入特征顺序必须与每次预测一并记录（forecast_decision 表），确保后续可以复现预测结果。SSE 路径置于 `/stream` 下，与 REST 平级。

## 7 部署与交付设计

本章定义系统从"原型代码"到"客户可部署运行"的交付形态。交付目标：客户（防汛部门）获得一个部署包，按手册即可在服务器上运行。

### 7.1 交付形态与总体策略

### 7.2 容器划分（M5 可选）

2. 执行 `generate_demo_data.py` 生成/重置模拟数据（可选）
3. 执行 `start.ps1`（Windows）/ `start.sh`（Linux）启动后端与前端（dev 模式或构建产物）
4. 访问 `http://localhost:8000/health` 验证三态 OK；前端访问对应端口

**M5（Docker 模式，可选）**：
1. 服务器安装 Docker 与 docker-compose
2. 解压交付包，编辑 `.env` 与 `config.yaml`（点位、阈值、数据源）
3. 执行 `./deploy.sh`（或 `docker compose up -d`）：启动容器 + 初始化（建库、示例数据、模型）
4. 访问 `http://<服务器IP>/` 验证；`GET /api/v1/health` 三态 OK
5. 升级：替换镜像 → `docker compose up -d` 重建，数据 volume 保留

### 7.4 环境与资源要求

| 项 | 要求 |
|---|---|
| 操作系统 | Windows 10+ / Linux（Ubuntu 20.04+）；Docker 模式要求服务器为 Linux |
| 最低配置 | 2 核 CPU / 4GB 内存 / 50GB 磁盘（纯 CPU，无 GPU 需求） |
| 推荐配置 | 4 核 CPU / 8GB 内存 / 100GB 磁盘 |
| 网络 | 能访问真实数据源接口则接真实数据；否则使用内置模拟数据演示 |
| Python | 3.11（锁版本） |

### 7.5 配置外置与数据持久化

- `config/default.yaml`：数据源类型（simulated/real）、模型类型、预见期（`lead_hours: [1,3,6,12]`，可撤回为 `[1,3]`）、预测周期、Agent 相关配置段
- `config/stations.yaml`：监测点列表与四级阈值、base_level、response_k
- `.env`：端口、数据库路径、VITE_USE_MOCK 等环境覆盖
- 持久化数据（SQLite/Parquet/checkpoints）不随容器或进程销毁，升级与回滚均安全

### 7.6 离线部署（政务内网场景）

部分客户部署在隔离内网，无法拉取公网依赖。方案：

- Docker 模式：交付包内含镜像归档（`docker save` 导出 tar，客户 `docker load` 导入）；提供 `offline-install.sh`；第三方 Python 依赖全部打入镜像
- 脚本模式：提供离线 wheel 目录（`pip install --no-index --find-links=./wheels`），依赖清单极简使离线包体积可控
- 地图不做：政务内网无公网瓦片 + 涉地图合规审图号（前端规划书范围外项）

### 7.7 运维与可观测性

- 健康检查：`GET /api/v1/health` 返回数据源、模型、数据库三态
- 日志：structlog JSON 结构化日志 + 按天滚动；trace_id/session_id 贯穿
- 任务状态：`task` 表记录长任务状态与失败原因
- 数据备份：定时备份脚本（SQLite dump + Parquet 目录）

## 9 演进路径

1. **接真实数据**：实现 `RealSourceAdapter`，改配置 `datasource.type: real`，业务层不动
2. **换真模型**：新增 `LgbmModel` 实现 `ForecastModel`，改配置 `forecast.model: lgbm`，业务层不动
3. **接入 Agent-B**：实现 `Agent` Port（LangGraph 或自研），复用已有 `ToolRegistry`；前端打开真实接口开关即可
3b. **升级 Agent-A**：`RuleBasedOrchestrator` → bandit/RL 选模型或 LLM 生成策略，调用方不变
3c. **接真实 NWP**：替换 `rain_forecast` 取数实现，6h/12h 链路无需改动
4. **暴露 MCP**：`api/mcp/` 填充实现，外部 Agent 客户端可直接调用
5. **加精度评估**：基于 `forecast_point.actual_level` 回填，无需改表结构
6. **地图**：须先解决离线瓦片与合规审图号，再引入 Leaflet / 本地 GeoJSON

以上各步**均不需要修改应用层与领域层代码**——这是模块化单体 + 端口适配器架构的全部价值所在。
