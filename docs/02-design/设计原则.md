# 设计原则与项目理念

> 本文档是整个项目的"宪法"。任何技术取舍与需求冲突，先回到本文档裁决。

## 1. 项目本质

这不是一个"预测水位准不准"的算法项目，而是一个：

> **面向城市防汛场景的、结构完整、可填充、可演进的 Agent 化工程骨架。**

算法精度本期不考核，骨架的可填充性、可扩展性、可演示性才是交付物。

## 2. 十条铁律

### P1 占位 ≠ 缺失
每一处留白都必须是"看得见形状的空位"：接口签名完整、能返回符合契约的数据、明确标注将来填什么、怎么填。评审时一眼看出扩展点。

### P2 依赖极简
任何存在安装失败风险的依赖一律不进 requirements.txt。一条命令跑不起来，骨架就是失败的。先进性体现在抽象和分层上，不体现在引入多少框架。

### P3 配置驱动一切
数据源类型、模型类型、点位、阈值全部外置。接真实数据、换模型，是"改配置 + 填一个实现类"，不是"改结构"。

### P4 模块化单体 + 端口适配器
物理上单进程（零运维），逻辑上按领域切分。应用层与领域层只依赖 Port 抽象，不 import 具体 Adapter。将来拆微服务只换适配器，业务代码不动。

### P5 前后端可独立启动
前端靠 mock 能跑全部页面，后端靠占位模型能返回全部接口。两边互不阻塞。

### P6 Agent 双层定义
- Agent-A（预测编排）：本期规则驱动做实，零 LLM 依赖
- Agent-B（交互会话）：本期 EchoAgent 占位，接口位留好
- Tool 抽象本期就做实：把系统能力声明式暴露，供将来 Agent 调用

### P7 骨架可读性 > 功能深度
优先服务"后续接手的模型工程师"和"评审方"：新人能看懂往哪填、扩展点在哪，比功能堆得多更重要。

### P8 三层交付边界
- 骨架层（目录/接口/数据模型/日志）：必须做实
- 原型层（页面/接口/演示链路）：形态到位，逻辑可简
- 占位层（真实数据源/真实模型/推送）：有接口 + 有占位 + 有标注

### P9 决策反转必须留痕
任何推翻之前决策的改动（如 Pinia 从不引到引入），必须在文档里写清楚"为什么反转"。这是演进记录，不是随意变更。

### P10 部署零运维
一条命令启动，≤3 步、≤2 分钟到页面可访问。现场无外网、无专业运维也能跑。

## 3. 技术取舍原则

| 场景 | 选什么 | 为什么 |
|---|---|---|
| 预测模型 | numpy 实现优先，不引重 ML 库 | 装得上跑得动 |
| 实时通信 | REST + 轮询，SSE 预留 | 不引入 WS 复杂度 |
| 数据库 | SQLite 写 + Parquet 分析 + DuckDB 查询 | 零服务、零迁移 |
| 前端 | Vue3 + TS + Element Plus + ECharts | 类型安全是 Agent 场景刚需 |
| 地图 | 一张图组件用 HTML/CSS 画 | 不引 Leaflet，先把演示跑通 |
| 气象数据 | 真接 Open-Meteo，失败 fallback 模拟 | 能不 mock 就不 mock |

## 4. 永不妥协的红线

- 不硬编码服务器 IP、密钥、个人路径
- 不因为赶进度跳过扩展点标注
- 不在领域层 import 基础设施层实现
- 不上传含敏感信息的文档到公开仓库
