# 架构升级与 Agent 预留设计说明

**版本**：V1.2（在《需求分析与技术选型》V1.1 基础上的架构升级）
**日期**：2026-10-03
**升级动因**：① 要求架构更先进、可扩展；② 明确本项目后续要演进为 **Agent 项目**，本期须预留接入位

---

## 1. 升级动因与边界

V1.1 的核心约束是"**能否稳定安装、骨架能否跑起来**"，这条仍然成立，**本次升级不推翻它**。V1.2 要解决的是另一个问题：

> V1.1 保证了"现在能跑"，V1.2 要保证"将来加 Agent 不用重构"。

因此本次升级的原则是：

1. **架构先进 ≠ 依赖重**。先进性体现在分层、抽象、契约与可演进性上，不体现在引入多少框架。
2. **Agent 本期是占位层**，但**接口位必须现在留好**——这是全篇最重要的一条。
3. 任何新增依赖仍须通过"能否稳定安装"这一关。

---

## 2. 架构范式：模块化单体 + 端口与适配器

### 2.1 为什么不拆微服务

"可扩展"不等于"微服务"。对本项目（单机 demo、后续演进为 Agent 应用），微服务带来的分布式复杂度远超收益。正确答案是 **模块化单体（Modular Monolith）+ 端口与适配器（六边形架构）**：

- **物理上单进程**：一条命令启动、零运维、调试简单（满足 NFR）
- **逻辑上按领域切分**：模块间只通过接口（Port）通信，不直接互相 import 实现
- **将来可拆分**：若某模块（如预测引擎、Agent 运行时）需要独立部署，只需把该模块的实现替换成远程调用适配器，**业务层代码不动**

### 2.2 分层结构

```
┌─────────────────────────────────────────────────────┐
│  接入层  API(REST v1) / SSE(流式) / MCP(占位)         │
├─────────────────────────────────────────────────────┤
│  应用层  用例编排：预测用例、研判用例、Agent 会话用例   │
├─────────────────────────────────────────────────────┤
│  领域层  实体 + Port（抽象接口）                      │
│          DataSource / ForecastModel / Tool / Agent   │
├─────────────────────────────────────────────────────┤
│  基础设施层  各 Port 的具体实现（Adapter）            │
│          SimulatedSource / NaiveModel / SQLRepo ...  │
└─────────────────────────────────────────────────────┘
```

**铁律**：应用层与领域层**不得 import 任何具体 Adapter**，只依赖 Port。这条保证了可替换性，也是 `grep EXT-POINT` 能穷尽所有待填点的前提。

### 2.3 四个核心抽象（V1.1 的两个 → V1.2 的四个）

| 抽象（Port） | 职责 | 本期实现 | 将来填充 |
|---|---|---|---|
| `DataSource` | 数据接入 | `SimulatedSource` ✅ | `RealSourceAdapter` 🔶 |
| `ForecastModel` | 水位预测 | `NaiveModel` / `LinearResponseModel` ✅ | LightGBM / TCN / LSTM 🔶 |
| **`Tool`** 🆕 | 把系统能力暴露为可被 Agent 调用的函数 | `ToolRegistry` ✅（本期即真实现，见 §4.3） | 工具持续扩充 |
| **`Agent`（B）** 🆕 | 会话编排与推理（交互智能体） | `EchoAgent`（占位）🔶 | LangGraph / 自研编排 🔶 |
| **`ForecastOrchestrator`** 🆕🆕 | 预测编排智能体（**Agent-A**） | `RuleBasedOrchestrator` ✅（纯规则，零依赖） | bandit/RL 选模型、LLM 生成策略 |

> **`Tool` 是四个抽象里唯一"本期就做实"的**。理由见 §4.2——它不是为 Agent 单独开发的功能，而是把已有 REST 能力做一层声明式封装，成本极低，收益极大。

## 3. 技术栈升级项（V1.1 → V1.2）

| 层 | V1.1 选型 | V1.2 选型 | 变更理由 |
|---|---|---|---|
| 架构范式 | 分层 MVC 式 | **模块化单体 + 端口适配器** | 可替换性与可演进性 |
| 数据访问 | SQLAlchemy 裸用 | **SQLAlchemy 2.0 + Alembic 迁移** | 数据库演进有版本管理，将来加 Agent 相关表不影响既有数据 |
| 分析查询 | SQLite | **SQLite（写入）+ DuckDB（分析）** | DuckDB 直接读同一批 Parquet 文件，零服务、零迁移、单文件安装。需要跨站点聚合分析时不必换数据库 |
| 配置 | Pydantic Settings | **Pydantic Settings（分层配置 + 环境覆盖）** | 保持，补充 Agent 相关配置段 |
| 日志 | 标准 logging | **结构化日志（JSON）** | Agent 场景需要 trace 关联（session_id / trace_id 贯穿） |
| 任务 | APScheduler | **APScheduler + 任务表**（长任务占位） | Agent 调用可能是长任务，需要可查询状态的任务抽象 |
| 实时通信 | REST + 轮询 | **REST + 轮询；SSE 预留** | Agent 流式输出用 SSE 比 WebSocket 更合适，见 §4.7 |
| 前端语言 | JavaScript | **TypeScript** | Agent 返回结构化数据，类型安全是刚需 |
| 前端状态 | 不引入 Pinia | **引入 Pinia** ⚠️ 反转 | 反转理由见 §3.1 |
| 前端 API 契约 | 手写封装 | **OpenAPI 自动生成 TS 类型与 client** | 前后端契约单一事实来源，杜绝手写不同步 |
| 依赖注入 | 无 | **FastAPI `Depends`** | 便于测试时替换 Adapter |

### 3.1 关于 Pinia 的反转说明

V1.1 曾决定"本期不引入 Pinia（状态规模小）"。**V1.2 反转，理由如下**：

1. Agent 会话是**跨页面共享的有状态数据**（会话列表、当前会话消息流、流式接收中的 token），靠组件本地 ref 无法管理；
2. SSE 流式输出需要在组件外累积状态；
3. 引入成本仅一个轻量库，而后期补做要改大量组件。

> 这属于"新需求导致的前置条件变化"，不是决策反复。凡此类反转，均需在文档中记录原因——正是这条记录让它成为可追溯的演进而非随意变更。

### 3.2 关于 DuckDB 的补充说明

DuckDB 是本次"先进且可扩展"的一个关键选择：

- `pip install duckdb` 约 30 MB，纯 wheel，Windows 安装无风险（不违反 NFR-1）
- **零服务进程**，像 SQLite 一样嵌在应用里
- 可直接查询 Parquet 文件：`SELECT * FROM 'data/*.parquet' WHERE station_id = 1`，**与现有 Parquet 存储方案完全兼容，无需数据迁移**
- 将来的 Agent 要做"跨站点聚合分析""历史相似事件检索"，DuckDB 的向量化执行远优于 SQLite

它不是时序数据库集群，而是在"不引入运维负担"前提下获得的分析能力——这正是本项目需要的取舍点。

## 4. Agent 预留架构（核心章节）

### 4.0 双层 Agent：先分清"智能体"指什么（V1.3 补充）

需求书措辞为"多模态 AI 趋势预测模型：时序预测模型 + AI 算法 + **智能体**"——此处"智能体"与预测模型并列，语义是**模型具备自适应、自融合能力**；而 §4 原设计的是**对话式工具调用 Agent**。两者不是一回事，**不做二选一，做双层**：

| | **Agent-A 预测编排智能体** | **Agent-B 交互智能体** |
|---|---|---|
| 对应需求书措辞 | "时序预测模型 + 智能体" | "智能体（辅助决策）" |
| 形态 | 应用层内部的**决策组件** | 对话式，工具调用 |
| 是否需要 LLM | **否**（规则驱动即可） | 是（填充阶段） |
| 本期实现 | `RuleBasedOrchestrator` ✅ | `EchoAgent` 🔶 |

**Agent-A 的五项决策**：模型自适应选择 / 多源融合权重 / 修正策略 / 置信区间自适应 / 降级决策，全部写入 `forecast_decision` 表。

**两层如何打通**：Agent-B 新增工具 `explain_forecast(forecast_id)`，直接把 Agent-A 的决策记录翻译成人话。这样"两个智能体"在系统内自洽，不是各说各话。

**演示价值**：Agent-A 不需要任何 LLM 或联网即可演示——注入数据缺失 → 融合权重变化 → 预测曲线变化 → 决策表可查。这是"智能体特性"最直观的证明，且成本极低。

### 4.1 为什么本期不引入 Agent 框架

尽管目标是 Agent 项目，本期**不建议**引入 LangChain / LangGraph / AutoGen 等框架：

1. **框架迭代极快**，现在锁定选型，半年后大概率过时；
2. **依赖体积与不确定性**，与"能否稳定安装"的硬约束冲突；
3. **Agent 的成败不在框架，而在数据与工具**（见 §4.8）——这些本期就能准备好。

正确做法是：**本期把"接口位 + 工具 + 数据"三件事做实，框架作为最后一个填充项**。到时候无论用 LangGraph 还是自研编排，都只是实现 `Agent` 这个 Port。

### 4.2 Tool 抽象为什么本期就做实

`Tool` 不是"为将来准备的成本"，它本期就有三重收益：

1. **成本近乎为零**：工具函数就是现有 Service 方法的声明式包装（补一段 JSON Schema 描述），不写新逻辑；
2. **让 REST 层与能力层解耦**：REST 路由与 Tool 都调用同一批 Service，能力只有一份实现；
3. **本期即可演示**：即使 Agent 是占位实现，也可以用"工具注册表 + EchoAgent"演示一次完整的"用户提问 → 选工具 → 执行 → 回答"链路，这是 Agent 项目最有力的早期验证。

### 4.3 Tool 注册表与工具清单

```python
class Tool(Protocol):
    name: str                      # 唯一标识
    description: str               # 给 LLM 看的用途说明（决定调用准确率）
    parameters: dict               # JSON Schema
    risk_level: Literal["L0","L1","L2"]   # 见 §4.4
    async def execute(**kwargs) -> ToolResult
```

| 工具 | 风险级 | 说明 | 本期 |
|---|---|---|---|
| `list_stations` | L0 | 列出监测点与当前状态 | ✅ |
| `get_station_status` | L0 | 查询单点位详情与预警状态 | ✅ |
| `get_level_series` | L0 | 查询历史水位/降雨序列 | ✅ |
| `run_forecast` | L0 | 对某点位发起预测 | ✅ |
| `get_active_alerts` | L0 | 查询生效预警列表 | ✅ |
| `explain_alert` | L1 | 解释某条预警的成因（阈值、峰值、降雨贡献、模型版本） | ✅ |
| `explain_forecast` | L1 | **解释 Agent-A 的编排决策**（为何选此模型、融合权重、修正强度） | ✅ V1.3 |
| `calibrate_params` | L1 | 标定模型参数（响应权重、退水系数），返回前后误差对比 | ✅ V1.3 |
| `query_forecast_accuracy` | L1 | 查询某点位预测精度 | 🔶 依赖指标计算 |
| `draft_alert_report` | L1 | 生成预警报告草稿（结构化，非自由文本） | 🔶 |
| `search_similar_events` | L1 | 检索历史相似内涝事件 | 🔶 依赖事件库 |
| `propose_threshold_change` | L2 | **建议**调整阈值，给出依据，不直接改 | 🔶 |
| `update_station_threshold` | L2 | 实际修改阈值（**必须人工确认**） | 🔶 |

### 4.4 Agent 能力分级与 Human-in-the-loop

防汛是**高后果场景**，Agent 不能拥有无约束的写权限。定义四级能力，本期只开放到 L2：

| 级别 | 能力 | 是否需要人工确认 | 本期 |
|---|---|---|---|
| **L0** | 只读查询 | 否 | ✅ 开放 |
| **L1** | 生成内容（报告、解读、建议） | 否（产物仅供人参考） | ✅ 开放 |
| **L2** | **建议**变更（阈值、配置） | **是，必须确认** | ✅ 开放"建议"，执行需确认 |
| **L3** | 自动执行（发布预警、推送、改配置） | — | ❌ **永不做** |

> **L3 永久不做**应写入系统设计约束。理由是责任归属：防汛预警的发布责任必须由人承担，Agent 自动发布一旦误报或漏报，无法追责。这一条在答辩时是加分项，说明你考虑过业务边界而不只是技术可行性。

### 4.5 MCP 暴露（可选加分项）

**MCP（Model Context Protocol）** 已成为 Agent 调用外部能力的通行协议。建议把 `ToolRegistry` 通过 MCP Server 暴露（占位实现）：

- 任何支持 MCP 的客户端（Claude Desktop、Cursor、自研 Agent）都能直接调用本系统能力
- 这是"可扩展"的最直接证明：**系统不绑定任何一家 Agent 框架**
- 本期只需在 `api/mcp/` 下留路由与 `EXT-POINT(INTEGRATION)` 标注

### 4.6 会话、追踪与可观测性

Agent 项目必须有 trace，否则出错无法定位。本期预留数据模型：

| 表 | 用途 |
|---|---|
| `agent_session` | 会话（id、创建时间、关联用户/场景、状态） |
| `agent_message` | 消息流（role、content、时间戳、token 用量） |
| `agent_tool_call` | 工具调用记录（工具名、入参、出参、耗时、是否成功） |

**这不只是给 Agent 用的**：`agent_tool_call` 天然成为系统操作的审计日志，对防汛业务有独立价值。

### 4.7 流式输出：SSE 优先于 WebSocket

Agent 的 token 流式输出是刚需。选型判断：

| 维度 | SSE | WebSocket |
|---|---|---|
| 方向 | 服务端→客户端（单向） | 双向 |
| 实现复杂度 | 低（就是 HTTP） | 高（握手、心跳、重连） |
| 自动重连 | 浏览器原生支持 | 需自行实现 |
| 穿透代理/网关 | 好（普通 HTTP） | 常被网关掐断 |
| 适用场景 | **LLM token 流、事件推送** | 高频双向交互 |

**结论**：
- Agent 流式输出与预警事件推送 → **SSE**
- 实时水位高频波形（若将来做）→ 才考虑 WebSocket
- V1.1 已裁决的"本期 REST + 轮询"不变；SSE 在 M5 或 Agent 阶段引入

### 4.8 Agent 项目的真正瓶颈：数据，不是框架

这是本节最想强调的一点。

**Agent 能不能真正有用，取决于它能不能查到结构化、可关联的数据。** 本系统恰好在生产这些数据，因此现在就要按"可被 Agent 查询"的标准来设计存储：

| Agent 会问的问题 | 需要的数据 | 本期状态 |
|---|---|---|
| "现在哪个点最危险？" | 点位 + 实时水位 + 生效预警 | ✅ 已有 |
| "这次预警是怎么算出来的？" | 预测明细 + 模型版本 + 特征口径 | ✅ `forecast_point` 已预留 |
| "过去类似降雨淹到过什么程度？" | **内涝事件库** | 🆕 需新增 `flood_event` 表 |
| "预测到底准不准？" | 预测-实况对齐数据 | ✅ `forecast_point.actual_level` 已预留 |
| "按预案该干什么？" | 防汛预案知识库 | 🔶 占位（向量检索后续做） |

**新增 `flood_event` 表**（事件库）是本期建议补的数据模型：

```
flood_event(
  event_id, station_id, start_time, end_time,
  peak_level, peak_time, total_rainfall, max_rain_intensity,
  max_alert_level, response_actions TEXT, remark TEXT
)
```

它同时服务三件事：Agent 的历史类比检索、模型训练的极端样本来源、演示时的"历史事件回放"。

> **判断**：很多 Agent 项目失败，是因为先搭框架再找数据，结果发现系统里没有可供查询的结构化资产。本项目的顺序应该反过来——**先把资产沉淀好，Agent 是水到渠成的最后一层**。

## 6. 风险与约束

| 风险 | 说明 | 缓解 |
|---|---|---|
| 架构过抽象导致开发变慢 | 端口适配器会增加一层间接 | **只在四个核心抽象上用**，其余保持直接调用。不为抽象而抽象 |
| DuckDB 引入后两套查询路径 | SQLite 写、DuckDB 读可能不一致 | 约定：**业务读写走 SQLite，分析查询走 DuckDB 读 Parquet**，Parquet 为唯一分析数据源 |
| TS 与自动生成的 client 增加前端门槛 | 需要装 Node 工具链 | 生成脚本纳入 npm script，一条命令；mock 通道保证后端未就绪时也能开发 |
| Agent 占位被误解为"没做" | 评审时可能质疑 | 坚持"占位 ≠ 缺失"：Tool 注册表本期做实、`EXT-POINT` 标注齐全、可演示完整工具调用链路 |
| 能力分级被绕过 | 后续开发者图省事让 Agent 直接改配置 | 在 `Tool.risk_level` 上做**运行时强制校验**，L2 无确认令牌则拒绝执行 |

## 7. 与 V1.1 的关系

V1.1 的所有硬约束继续有效：三层交付边界、占位≠缺失、`EXT-POINT` 标注、`forecast_point` 明细表、不引入高风险依赖、Python 3.11。

V1.2 是**在其之上的架构增强**，不改变交付范围（仍是脚手架 + 可运行原型），只改变实现方式与预留深度。里程碑仍是 M1–M5，但各阶段的产出物增加相应内容（详见前后端规划书 V2.0）。
