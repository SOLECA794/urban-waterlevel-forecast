## 2. 缺口①：智能体语义 —— 双层 Agent 架构

### 2.1 问题

需求书写的是"**多模态 AI 趋势预测模型：时序预测模型 + AI 算法 + 智能体**"。这句话里"智能体"是**跟预测模型并列**的，语义更接近"模型具备自适应、自融合的能力"。

V1.2 规划的 Agent 是**对话式工具调用**（问答、报告、阈值建议），是另一个语义。

两者都对，但只做一个会漏。**处置方式：不做二选一，做双层。**

### 2.2 双层 Agent 定义

| | **Agent-A：预测编排智能体** | **Agent-B：交互智能体** |
|---|---|---|
| 全称 | `ForecastOrchestrator` | `Agent`（V1.2 已有） |
| 对应需求书措辞 | "时序预测模型 + AI 算法 + **智能体**" | "多模态 AI + **智能体**（辅助决策）" |
| 位置 | 应用层内部组件 | 接入层之外，通过 Tool 调用系统 |
| 形态 | 非对话、非 LLM，是**决策组件** | 对话式，工具调用 |
| 本期实现 | `RuleBasedOrchestrator`（规则驱动，纯 Python） | `EchoAgent`（占位） |
| 将来升级 | RL / bandit 选模型、LLM 策略生成 | LangGraph / 自研编排 |
| 是否必须联网/LLM | **否** | 是（填充阶段） |

### 2.3 Agent-A 的五项决策职责

`ForecastOrchestrator` 在每次预测前做出以下决策，全部记录、全部可解释：

| # | 决策 | 输入依据 | 本期规则示例 |
|---|---|---|---|
| D1 | **模型自适应选择** | 预见期、历史数据充足度、各模型近期误差 | 数据 < 阈值 → NaiveModel；否则 LinearResponse；6h/12h 强制启用预报输入 |
| D2 | **多源融合权重** | 各数据源质量（延迟、缺失率、近期与实况偏差） | 权重 ∝ 1/(1 + 近期偏差)，归一化 |
| D3 | **修正策略** | 当前新息大小、数据源新鲜度 | 新息 > 阈值 → 启用修正，α 取 0.6 |
| D4 | **置信区间自适应** | 近期误差水平、预见期长度 | 区间宽度 ∝ 近期 RMSE × √(h) |
| D5 | **降级决策** | 数据源状态 | 断流 → 降级为 NaiveModel 并标注"数据延迟" |

**为什么这样设计就对了**：需求书说的是"模型带智能体特性（自动融合多源、自适应选算法）"——上面 D1/D2 正是这两件事的字面实现。而它**不需要 LLM、不需要联网、纯规则即可跑**，完全符合脚手架阶段的依赖约束。

### 2.4 决策可追溯：`forecast_decision` 表

```sql
CREATE TABLE forecast_decision (
  forecast_id     INTEGER NOT NULL,
  selected_model  VARCHAR(32) NOT NULL,   -- D1
  fusion_weights  TEXT,                   -- D2，JSON
  revision_alpha  REAL,                   -- D3
  ci_scale        REAL,                   -- D4
  degraded        BOOLEAN,                -- D5
  reason          TEXT,                   -- 人话解释（给前端与 Agent-B 用）
  create_time     DATETIME NOT NULL
);
```

**这张表同时服务三件事**：
1. 预测结果可复现、可解释（V1.1 NFR-7）
2. **Agent-B 的 `explain_forecast` 工具直接读它**，两个 Agent 在此打通
3. 演示时可直接展示"系统为什么选了这个模型"——这是"智能体特性"最直观的证明

### 2.5 双层的统一：共用 Tool 与决策表

```
用户提问
   ↓
Agent-B（对话式）──调用 Tool──→ 系统能力
   ↓                              ↑
生成解读/报告  ←──读 forecast_decision──┘
                                  ↑
                    Agent-A 在每次预测时写入决策
```

Agent-B 新增一个工具 `explain_forecast(forecast_id)`，直接把 Agent-A 的决策过程翻译成人话。**这样"两个智能体"在系统里是自洽的一体，不是各说各话。**

### 2.6 如果老师指的是另一种语义

| 老师实际所指 | 我们的应对 |
|---|---|
| "模型带自适应/自融合能力" | → **Agent-A 已做实**（规则驱动，本期可演示权重与模型选择的变化） |
| "对话式智能体辅助决策" | → **Agent-B 已预留**（Tool 注册表本期做实，Agent 实现位待填 LLM） |
| 两者都要 | → 双层架构本来就是一体，不需要改结构 |

## 3. 缺口②：多源协同修正 —— `ForecastRevisionService`

需求书原文："多源协同修正：滚动校正（结合实时监测、最新预报、已发生事件）"。

V1.2 只有"滚动预测"（重新算一遍），**没有"用已发生的事实去修正尚未发生的预测"这一环**。这是本质差别，必须补。

### 3.1 三类触发

| 触发 | 对应需求书措辞 | 说明 |
|---|---|---|
| T1 | 实时监测 | 新的水位/雨量实测到达 |
| T2 | 最新预报 | 降雨预报刷新 |
| T3 | 已发生事件 | 进入退水期 / 已记录内涝事件 |

### 3.2 修正算法：多源加权新息 + 时间衰减

**第一步：算各源的新息（innovation，即"最近预测错了多少"）**

```
e_level  = actual_level(t_now)  - predicted_level(t_now)
e_rain   = Σ(actual_rain - predicted_rain)  over 最近窗口
e_fcst   = 最新预报量 - 上一版预报量
```

**第二步：多源加权合成总新息**

```
e = w_level · e_level + w_rain · e_rain + w_fcst · e_fcst
```

权重 `w` 由 **Agent-A 的 D2 融合权重**给出——这正是"多源协同"的字面实现，且与 Agent-A 打通。

**第三步：对未发生时段做衰减修正**

```
corrected(t) = predicted(t) + α · e · ρ^(Δt)
```

- `α`：修正强度（Agent-A D3 决策，默认 0.6）
- `ρ`：时间衰减因子（默认 0.85 / 步）——**越远的未来修正越少**，符合"近期可信、远期不确定"的直觉
- `Δt = t − t_now`，仅对 `Δt > 0` 的时段生效

**第四步：同步调整置信区间**

```
width(t) = width_raw(t) · (1 + β · Δt)     # 越远越宽
```

### 3.3 存储：`forecast_point` 扩展字段

```sql
ALTER TABLE forecast_point ADD COLUMN pred_level_raw REAL;  -- 模型原始输出
ALTER TABLE forecast_point ADD COLUMN revision      REAL;   -- 修正量（可正可负）
-- pred_level 语义变更为"修正后对外输出值"
```

**这一改同时解决两件事**：
1. 协同修正可追溯（原始 vs 修正后可对比）
2. V1.1 FR-3.7 要求的"原始模型输出与平滑后曲线同时保存"一并落地，不用再加表

### 3.4 与"在线学习"的关系（顺带把校准项也补齐）

| 层次 | 做法 | 本期 |
|---|---|---|
| **预测级在线适应** | 新息修正（本节）——不改模型参数，只修正本次输出 | ✅ **做实** |
| 模型级在线学习 | 增量训练更新模型权重 | ❌ 不做（稳定性风险高，且演示价值为零） |

> 这是有依据的取舍，不是偷懒：模型级在线学习在水位这种**小样本、强非平稳**场景极易发散，一旦发散整个演示就崩。而预测级修正**可随时关闭、失败也只是回到原始预测**，风险可控。

### 3.5 演示价值

详情页可同时画出三条线：**原始预测（细虚线）+ 修正后预测（粗虚线）+ 实测**。修正带来的改善一眼可见——这是"多源协同修正"最好的证明方式。

## 4. 缺口③：6h/12h 预见期 —— 模拟源产出降雨预报序列

### 4.1 问题

V1.2 把 6h/12h 标为"依赖真实 NWP 数据，占位"。这是对需求书的缩水，且**理由不够充分**——因为"需要未来降雨预报"这件事，**模拟数据源自己就能造出来**。

### 4.2 方案：模拟源同时产出实况与预报两路降雨

```
rain_observed(t)              # 实况降雨（已有）
rain_forecast(t_issue, h)     # 在 t_issue 时刻对 t_issue+h 的降雨预报（新增）
```

预报误差建模（体现"预见期越长越不准"这一真实特性）：

```
rain_forecast(t, h) = rain_true(t+h) · (1 + ε(h))
ε(h) ~ N(bias(h), σ(h))，且 σ(h)、|bias(h)| 随 h 单调增大
```

还可加入**系统性低估**（真实 NWP 对强对流峰值的典型缺陷），让演示更真实。

### 4.3 效果

| 项 | V1.2 | **V1.3** |
|---|---|---|
| 6h/12h 状态 | 占位 ❓ | **✅ 本期跑通完整链路** |
| 输入来源 | 真实 NWP（无） | 模拟预报序列（有） |
| 真实场景切换 | 需大改 | 只需替换 `rain_forecast` 的取数实现 |
| 演示效果 | 无 | **可见"预见期越长、置信区间越宽"** |

**"预见期越长、区间越宽"本身就是一个很好的演示点**——它直观说明了不确定性传播，比只做 1h/3h 更有说服力。

### 4.4 研判侧配套：长预见期降权

长预见期不确定性大，若与 1h 同等对待会造成误报风暴。增加规则：

| 预见期 | 预警处理 |
|---|---|
| 1h / 3h | 正常生成预警 |
| 6h / 12h | 生成预警但**标记 `reference`（参考级）**，默认不推送、在界面以浅色区分 |

`alert` 表增加 `is_reference BOOLEAN`。这样既覆盖需求，又不牺牲预警可信度。

### 4.5 若老师仍认为不该做

默认已按"做"推进。若老师明确本期只要 1h/3h，砍掉成本极低——只是 `config.yaml` 里把 `lead_hours: [1, 3, 6, 12]` 改成 `[1, 3]`，代码不改。

## 5. 附带补齐：模型校准的三项落点

需求书"模型校准"含三项，V1.2 全部归为占位。V1.3 逐项落位：

| 子项 | V1.2 | **V1.3 落点** | 本期 |
|---|---|---|---|
| **重训** | 占位 | 保留占位（`/calibrations` 返回 pending） | 🔶 |
| **参数校准** | 未提及 | **做实**：网格/随机搜索标定 `LinearResponseModel` 的降雨响应权重 `wᵢ` 与退水系数 `k`（纯 numpy，几十个参数，秒级完成） | ✅ |
| **在线学习** | 未提及 | **做实（预测级）**：即 §3 的新息修正；模型级增量训练明确不做并说明理由 | ✅ |

**参数校准本期做实的意义**：它让"校准"这个词不再是空的——演示时可以现场跑一次参数标定，展示前后误差变化。成本仅一个小脚本 + 一个 `calibrate_params` 工具（L1 级）。

> 至此需求书"模型校准"一项从 🔶 部分覆盖 → ✅ 三项各有明确处置（一项占位 + 两项做实）。

## 7. 验收标准增补项

在原验收清单基础上增加以下可勾选项：

**原型层**
- [ ] 详情页可切换 1h / 3h / 6h / 12h，且**预见期越长置信区间越宽**

**骨架层**
- [ ] `ForecastOrchestrator` 决策可追溯：`forecast_decision` 表记录了模型选择、融合权重、修正强度与理由
- [ ] 数据源质量变化时，融合权重随之变化（可通过注入数据缺失演示）
- [ ] `forecast_point` 同时保存 `pred_level_raw`、`revision`、`pred_level`

**占位层**
- [ ] Agent-B（对话式）接口与 Tool 注册表就位，`explain_forecast` 可解释 Agent-A 的决策
- [ ] 模型级在线学习明确标注"不做 + 理由"，而非留白不明

## 8. 结论

三个缺口已全部补齐，且补齐方式遵循两条原则：

1. **不增加重依赖** —— Agent-A 规则驱动、协同修正是几十行 numpy、6h/12h 只是生成器多一路输出。全部零新增依赖。
2. **不做二选一的猜测** —— 智能体语义用双层架构同时覆盖两种可能，无论老师指的是哪种都对得上。

需求书逐条核对结果为**全部 ✅**，无遗留待补充事项。
