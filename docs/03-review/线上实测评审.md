## 2. 根因定位：观测数据生成器死了，不是预测调度器死了

这是本次评审最重要的发现，比两轮评审的"数据源滞后"更进一步。

### 取证

| 时间 | `data_age_min` | 最新样本时间戳 | 预测总条数 | 数据源状态上报 |
|---|---|---|---|---|
| 22:07 | 157.9 | 19:30:00 | 723 | STREAMING · 运行正常 |
| 22:11 | ~160 | 19:30:00 | 777 | STREAMING · 运行正常 |
| 22:16 | **166.6** | **19:30:00（未变）** | **825** | STREAMING · 运行正常 |

### 三个结论

1. **预测调度器活着**——forecasts 从 723 → 777 → 825 持续递增，说明定时任务在跑；
2. **观测数据生成器已死**——六站最新样本时间戳全部冻结在 `19:30:00`，`data_age_min` 随时间线性增长（157.9 → 166.6，约 1 分钟/分钟）；
3. **健康检查在误报**——数据已陈旧 166 分钟，状态仍上报"STREAMING · 模拟数据源运行正常"。这是比生成器死亡更严重的问题：**监控系统自己没发现系统坏了**。

### 推断与修复方向

**推断**：模拟生成器大概率被实现为"从起始时刻生成到某个固定结束时刻"的**一次性窗口**，窗口走完即停；也可能依赖的追加 tick 未随调度器启动。

**修复（三件事，缺一不可）**：

| # | 修复项 | 具体做法 | 验收 |
|---|---|---|---|
| R1 | 生成器改为滚动窗口 | 每次 tick 以 `now()` 为基准生成最近 N 个样本，永不耗尽；样本时间戳用**相对时间**而非固定起点 | 连续观察 30 分钟，`data_age_min` 始终 < 10 |
| R2 | 健康检查纳入新鲜度 | `data_age_min > 30` 时状态改判 `STALE` 并在顶部状态条变黄/红；不是"运行正常" | 人为停掉生成器 5 分钟后，状态条自动变 STALE |
| R3 | 生成器自愈 | 健康检查发现 STALE 时自动重启生成器并写日志 | 杀掉生成器进程后 2 分钟内自动恢复 |

**热修**：重启服务大概率临时恢复，但按上表不修会复发——生成器窗口总会再次走完。

## 4. 缺陷清单（合并去重，按优先级）

### P0-1 观测数据生成器停止供给 ★最高优先级

见 §2。三件套修复 R1/R2/R3。**不修它，后面每一项演示都是平线。**

### P0-2 Agent 控制台：内容已完备，只需补路由兜底

**推翻"白屏"判定**。实测 `/agent` 与菜单点击均完整渲染：会话管理、消息流、13+ 工具带 L0/L1/L2 分级、L2 确认令牌、工具调用轨迹，且对话链路实测成功。

**仍需修（10 分钟）**：
- 增加 `path: "/:pathMatch(.*)*"` 兜底路由，重定向到 `/` 或显示 404 页——**不存在的路由不能静默白屏**；
- 建议把 `/agent` 显式别名为 `/agents`，避免习惯性输入落空白屏。

### P1-3 精度评估空转（RMSE 全 "—"）

`forecast_point.actual_level` 事后回填未生效。需求书两处点名"实际值对比 / 效果评估"，是**验收硬点**。
修复：模拟场景让回填随数据流滚动执行（目标时刻一过、模拟实测落地即回填）；前端 RMSE 为空时显示"待回填"而非 "—"。

### P1-4 协同修正不可见（α=0，双曲线重合）

降级态设计上关闭修正（合理），但意味着**需求书三大算法之一在演示中永远看不到**。
修复：数据源修好后 α 自然非零；再加一个**"修正前后对比"高亮开关**，把两条线的差异区域染色，让评审者一眼看到"修正把预测拉向实测"。

### P1-5 决策面板自相矛盾

同一屏：横幅说"本次为降级预测（持久性模型）"，D1 却显示 `linear_response`（正常样式）。
修复：降级时 D1 显示**实际执行模型**（naive）+ 红色"已降级"标记。追溯面板自己不能矛盾——这是"全程可追溯"卖点的反面案例。

### P1-6 提前量展示（降级后复测）

当前 API 返回最近 20 条 `lead_minutes_advantage` 全为 0；历史期曾出现 118/133/158 分钟（第二轮评审所见，机制可信）。
修复：数据源修复后复测；若仍为 0，则查计算口径（疑似用同一预测时刻做差）。
**文案**（无论是否修复都要做）：`0 分钟` 改为"已超阈值，预警即时触发（提前量不适用）"，避免老师困惑。

### P1-7 "演示钥匙"缺失：无法主动注入暴雨事件

模拟源支持极端事件注入，但**没有入口**。导致演示只能被动等模拟器自己下雨，不可控。
修复：系统设置页加"注入极端降雨事件"按钮（下拉选站点 + 雨强档位）。
**建议从 P2 提级到 P1**——没有它，P1-4 / P1-6 的修复效果都无法在演示时按需复现。

### P2-8 "一张图"缺失（贴题硬缺口）

需求书原话"在一张图和趋势曲线上可视化展示"。因地图瓦片合规问题砍掉了 GIS，但**"一张图" ≠ GIS 地图**。
方案（零依赖）：总览页顶部加**站点示意图**——按站点类型（低洼段/下穿隧道/河道断面/泵站）排布的抽象平面，SVG 手绘即可；站点按预警等级着色（正常绿 / 黄 / 橙 / 红脉动），点击进入详情。

### P2-9 预警联动发布无踪迹（贴题硬缺口）

需求书原话"联动消息、信息屏或其他发布渠道"。推送本身是 EXT-POINT 占位，但**占位 ≠ 不可见**。
方案：预警中心加"发布记录"标签页，预警触发后生成 mock 记录（站内消息 ✅ / 信息屏模拟 ✅ / 短信占位灰显标 `EXT-POINT(INTEGRATION)`）。

### P2-10 体验类小项

| 项 | 现象 | 做法 |
|---|---|---|
| 预警中心首屏空表 | 截图瞬间显示"暂无数据 共 0 条"，1 秒后才渲染 28 条 | 加骨架屏 / loading 态 |
| 模型下拉被遮挡 | 自定义控件需二次定位 | z-index 与点击目标修正 |
| 水位口径不一致 | 卡片 2.08 与预测记录 2.07/2.09 并存 | 统一到同一时间戳口径，卡片标注"更新于 HH:MM" |
| 详情页首屏空图 | 进入后所有指标 "—"，须手动点"发起预测" | 自动加载最近一次预测 |
| 预警原因截断 | "超过黄色阈值 1.90 …" | 悬停 tooltip 显示全文 |
| Agent 建议 chips 不可点 | 只能手输 | 点击即填入输入框 |

## 5. 正常态 vs 降级态：演示时到底在演哪一套

这是第二轮评审最有价值的一句判断，保留并强化：

```
正常态（应该展示的）：
  多源融合 → 协同修正 α>0 → 双曲线分叉 → 提前量 X 分钟 → 预警 → 发布联动 → 事后 RMSE

降级态（当前正在跑的）：
  数据滞后 166min → D5 降级 → α=0 → 双曲线重合 → 提前量 0 → 标注"数据延迟"
```

**降级是兜底能力，不是主演出。** 老师看到降级态，只拿到"系统有兜底机制"这一个信息点，丢掉三个更有说服力的信息点。

**但要保留降级能力本身**——它是答辩亮点，讲法见 §7。

## 6. 这个 demo 应该做成什么样子

### 6.1 本质三句话

1. **水会涨**（多源数据进来：雨量、水位、气象预报）
2. **涨多少、什么时候涨到**（预测出去：多预见期 + 置信区间 + 协同修正）
3. **所以要提前做什么**（预警落地：分级研判 + 提前量 + 发布联动 + 事后评估闭环）

现状 1、2 骨架都在，3 只有"分级研判"落地。**老师目光会沿这三句走一遍，任何一句断了，demo 就退回"数据看板"。**

### 6.2 目标画像：一场不带 PPT 的 10 分钟演示

修完 P0/P1 后应能纯靠页面讲完：

| 幕 | 操作 | 观众看到什么 |
|---|---|---|
| ① 态势 | 打开总览 | **一张图**上六站安静地绿着，数据源 STREAMING 跳动 |
| ② 注入暴雨 | 设置页点"注入极端降雨事件" | 图上卡片由绿转黄，雨量柱升起，**历史水位开始抬头** |
| ③ 预测 | 点开 S001 详情 | 实线爬坡、虚线越过黄色阈值线、**置信区间随预见期变宽**、指标区显示峰值/峰值时间/**提前量 42 分钟** |
| ④ 修正 | 切 3h，看决策面板 | D1–D5：为什么选这个模型、三路权重、**修正后预测更贴近刚落地的实测**（α≠0，双曲线分叉） |
| ⑤ 预警 | 回预警中心 | 黄色预警"生效中"，提前量非零，**发布记录**显示消息/信息屏已模拟推送 |
| ⑥ 追问 | Agent 控制台 | "为什么选这个模型"→ 读决策记录答人话；"生成报告"→ L1 工具产出草稿；L2 工具需确认令牌 |
| ⑦ 复盘 | 次日视角 | RMSE 有值，"预测 vs 实际"对比可查，参数校准前后误差变化 |
| ⑧ 收尾 | 终端 | `grep -r "EXT-POINT" --include="*.py" .` → 列出全部留白位点 |

### 6.3 一条自检标准

每一页问自己：**这一屏能不能回答需求书里的原话？**

- 总览页 → "一张图可视化展示"（现在答不了 → P2-8）
- 详情页 → "趋势预测 + 多预见期 + 预警研判"（能答，但被 P0-1 压住）
- 预警中心 → "等级研判 + 联动发布"（发布答不了 → P2-9）
- 校准区 → "效果评估 + 实际值对比"（答不了 → P1-3）
- Agent 台 → "智能体"（**答得最响的一页**，实测链路完整）

## 7. 答辩叙事建议

修完之后，主动把"降级机制"从 bug 风险翻转为工程素养证明：

> "系统对数据新鲜度有健康检查——当数据源断流或滞后超过阈值，预测自动降级为持久性模型并在界面明示降级原因，而不是带着错误数据输出一个看似正常的预测。这是高后果预警系统应有的失效安全设计。"

**但前提是：正常情况下预测必须好看。** 所以顺序是——先修 P0-1 让它跑正常态，再讲降级机制作为加分项。倒过来讲会变成"你的系统是不是坏了"。
